# Codex·Gemini 완료 전 코드 품질 검토

Codex와 Gemini/Antigravity의 `Stop` 훅이 같은 대화에 검토 지시를 전달합니다. 코드·스크립트·동작 설정·문서·테스트·작업용 파일을 변경한 요청에서 산출물의 실제 용도와 잔여물을 확인하고, 변경에 해당하는 요구사항·AI 슬롭·과잉 설계·중복 구현·보안·버전 호환성을 점검합니다. 문제가 있으면 수정·검증 후 새 회차에서 재검토하고, 수정 없는 회차에서 미해결 문제가 없고 필요한 검증이 충족되면 종료합니다. 별도 모델·API 키·패키지는 필요하지 않으며 Node.js 22 이상을 사용합니다.

이 저장소의 `gemini/`는 기존 secret checker와 같은 **Google Antigravity용**입니다. 별도 제품인 Gemini CLI의 `AfterAgent`나 `.gemini/settings.json` 설정과는 구분합니다.

## 도구별 동작

| 도구 | 등록 파일 | 검토 재개 응답 | 검토 상태 확인 |
| --- | --- | --- | --- |
| Codex | 전역 `~/.codex/hooks.json`, 프로젝트 `.codex/hooks.json` | `decision: "block"`과 `reason` | `stop_hook_active`, `last_assistant_message` |
| Gemini/Antigravity | 전역 `~/.gemini/config/hooks.json`, 프로젝트 `.agents/hooks.json` | `decision: "continue"`와 `reason` | 현재 사용자 턴의 transcript 내 검토 요청과 마지막 모델 응답 |

Codex는 `UserPromptSubmit`, Antigravity는 현재 사용자 요청의 첫 `PreInvocation`에서 별도의 Node 감시 프로세스를 시작합니다. 준비 완료를 확인한 뒤 작업을 진행하며, 프로젝트 파일 전체 내용이나 해시를 읽지 않습니다. Git 루트와 추적 경로 목록 등 메타데이터는 확인합니다.

같은 사용자 턴의 준비 요청이 겹치면 이미 준비 중이거나 준비된 감시를 재사용합니다. 뒤늦은 준비 요청이 같은 턴의 감시를 종료하거나 변경 기록과 검토 예산을 초기화하지 않습니다.

새 턴은 Git 조회 전에 감시 소유권을 등록합니다. 등록 구간만 프로세스 간 잠금으로 보호하며, 종료된 프로세스의 잠금은 다음 준비에서 회수합니다. 이전 준비는 등록 당시의 감시만 정리하고, 소유권을 잃었으면 감시를 새로 시작하지 않습니다. 워커도 시작과 요청 처리 시 소유권을 확인합니다.

여러 작업 폴더의 Git 루트는 한 번에 최대 2개씩 조회합니다. 조회별 1초·stdout와 stderr를 합친 원본 바이트 1MiB 제한을 적용하고, 시간 초과나 실행 오류가 있으면 같은 배치의 조회가 끝난 뒤 준비 실패로 기록하며 다음 배치를 시작하지 않습니다. Git 미설치 또는 표준 비저장소 오류가 확인된 폴더는 해당 작업 폴더를 감시합니다. Git 설정 손상·권한 오류·프로세스 비정상 종료는 감시 범위를 줄여 계속하지 않고 준비 실패로 남깁니다. 오류 분류를 위한 Git 메시지는 C 로케일로 확인하며 원문은 상태 기록에 저장하지 않습니다. 입력 순서와 중복 Git 루트의 감시 제외는 유지합니다.

Git 루트가 여러 개면 추적 파일 목록도 최대 2개씩 조회하며, 하나면 기존 동기 조회를 유지합니다. 조회별 1초·stdout와 stderr를 합친 원본 바이트 4MiB 제한을 적용합니다. 준비 중 파일 이벤트는 대기열에 모으고, 추적 목록을 모두 읽은 뒤 추적·ignored 여부를 분류합니다. 따라서 ignore 패턴과 일치하는 추적 파일의 수정도 포함됩니다. 병렬 조회 실패 시 같은 배치의 종료를 확인한 뒤 준비 실패로 기록하고 다음 배치를 시작하지 않으며, 감시 종료 요청은 진행 중인 병렬 조회를 취소합니다. 두 조회가 동시에 응답 버퍼를 사용하므로 이 단계의 일시적인 메모리·CPU 사용량은 순차 조회보다 늘어날 수 있습니다.

감시 중 대상 파일 이벤트가 발생하면 `changed`를 true로 기록합니다. 직접 편집·터미널·서브에이전트 중 수정 경로와 관계없이 같은 감시 범위의 이벤트를 받습니다. 같은 내용으로 다시 저장하거나 수정 후 원복한 경우도 수정 발생으로 검토 대상입니다. 기존에 있던 사용자 변경은 감시 시작 전 상태이므로 그것만으로 검토하지 않습니다. 편집 시마다 모델을 호출하지 않습니다.

첫 대상 변경을 확인하고 상태를 저장한 뒤에는 모든 감시 루트의 Git 추적 경로 인덱스를 비우고, 추가 이벤트의 파일 정보 조회·Git 분류를 멈춥니다. 진행 중인 Git ignore 분류도 종료하며, 감시가 닫힐 때도 남은 분류 프로세스를 종료합니다. 종료 전에 예약된 이벤트 처리도 종료 후에는 대기열을 비우고 새 Git 분류를 시작하지 않습니다. 이후 불필요한 분류 오류가 이미 확인한 변경의 검토를 취소하지 않도록 하며, 감시 자체의 오류와 준비·Stop 시 probe/root 확인은 계속 적용합니다.

Git 추적 대상의 이벤트는 즉시 수정으로 확정합니다. 미추적 파일과 같은 배치에 있거나 이전 Git 분류가 아직 진행 중이어도 그 분류를 기다리지 않습니다. 추적 대상이 아닌 이벤트만 Git ignore 분류를 수행합니다. Git 없는 폴더도 첫 대상 이벤트에서 즉시 수정으로 확정해 같은 배치의 나머지 이벤트를 불필요하게 분류하지 않습니다.

Git ignore 분류에는 수집한 이벤트 집합을 요청 스냅샷으로 재사용하고, 분류 중 들어오는 이벤트는 별도 집합에 쌓아 다음 배치에서 처리합니다. 반환된 경로가 모두 요청 스냅샷에 포함되는지 확인한 뒤 집합 크기로 미제외 경로의 유무를 판단합니다. Git 출력은 UTF-8 스트림으로 해석해 한글·이모지 경로가 청크 경계에서 잘려도 보존합니다.

`Stop`은 로컬 통신으로 감시 상태와 수집된 이벤트 처리를 확인합니다. 수정 사실이 이미 기록됐으면 추가 이벤트 처리를 위한 고정 대기는 생략하며, probe 응답·루트 교체·확인 시간 제한과 감시 오류는 계속 검사합니다. 정상 감시에서 수정 기록이 없으면 추가 프롬프트나 상태 표식 없이 감시를 종료합니다. 수정 기록이 있으면 짧은 안내와 `REVIEW.md`의 절대 경로를 같은 대화에 전달합니다. 검토 반복 중에는 감시와 수정 상태를 유지하고, 최종 상태에서 감시를 종료합니다.

실행 중인 감시는 코드를 다시 불러오지 않으므로 워커 수정은 다음 사용자 요청의 새 감시부터 적용됩니다.

Git 프로젝트는 저장소 루트, Git이 없으면 작업 폴더를 재귀 감시합니다. Markdown·README 등 문서 변경도 포함합니다. `.git`·`node_modules`·`.venv`·`dist`·`build`·`coverage`·`target` 등 생성/의존성 폴더, Git ignored 경로와 링크 대상의 변경은 제외합니다. Git 추적 경로와 백업 후보 이름은 ignore 패턴과 일치해도 포함합니다. 백업 후보는 `backup`·`backups` 및 `backup-날짜` 같은 경로, `.bak`·`.backup`·`.orig`·`.rej` 확장자(날짜 접미사 포함), 끝이 `~`인 이름입니다. 생성/의존성 폴더와 링크 내부의 제외는 백업에도 우선합니다. 후보 감지는 검토를 시작할 뿐 파일을 삭제하지 않습니다. 폴더 삭제·이동·교체와 분류가 불명확한 구조 변경은 보수적으로 수정으로 판단할 수 있습니다. 감시 범위 밖의 수정은 감지하지 않으며, 사용자나 다른 프로그램이 같은 범위를 수정한 경우 AI의 수정과 구분하지 못합니다.

준비와 Stop에서 감시 응답성을 확인하기 위해 각 감시 루트에 `.ai-setting-quality-probe-<UUID>.tmp` 임시 파일을 생성·삭제합니다. 이 예약 이름은 모든 감시 프로세스에서 제외합니다. 작업 폴더 쓰기 권한이 필요하며, 예기치 않은 강제 종료 시 임시 파일이 남을 수 있습니다. probe 응답은 감시 연결의 동작 확인이며 OS 이벤트 무손실을 보장하지 않습니다.

작업 폴더 자체나 상위 경로가 junction·심볼릭 링크이면 준비 당시 실제 대상을 기록합니다. 시작과 Stop 확인에서 대상이 달라졌거나 경로가 사라지면 감시 실패로 보고하며, 새 대상으로 감시 기준을 바꾸거나 변경 없음으로 처리하지 않습니다. 프로젝트 내부의 링크 대상 제외와는 별개입니다.

감시 시작·오류·종료·root 교체·이벤트 경로 누락·분류 실패·통신 실패는 수정 없음으로 취급하지 않습니다. 감시 실패는 자동 검토 미완료 경고로 남기고 사용자 작업이나 모델을 차단·재개하지 않습니다. Codex는 `systemMessage`, Antigravity는 stderr로 경고하며 실패 때문에 별도 모델 프롬프트나 `blocked` 응답을 요구하지 않습니다. Antigravity 경고의 화면 표시는 호스트에 따라 달라지므로 실행 로그도 확인합니다. 같은 요청의 실패한 감시를 새 기준으로 자동 재시작하지 않습니다. 정상 완료·상한·실패 등 종료 기록이 남은 요청은 반복 Stop이나 Antigravity PreInvocation에서도 재개하지 않습니다. 새 명시적 사용자 요청에서만 새 감시와 예산을 시작합니다. 준비 기록 유실을 새 기준으로 재준비하지 않으며, Antigravity는 현재 요청의 모델 응답이 이미 시작됐다면 기록을 잃어도 새 감시를 만들지 않습니다. 이전 해시 방식의 진행 중 기록도 새 감시로 승계할 수 없으므로 감지 실패로 처리하며 새 사용자 요청부터 감시합니다.

감시는 정상 종료·감지된 실패와 같은 대화의 다음 요청에서 정리합니다. 중단 등으로 종료를 받지 못한 고아 프로세스는 최대 24시간 후 실패 상태를 남기고 종료합니다. 이 제한은 리뷰 통과를 뜻하지 않으며 아래의 별도 리뷰 횟수 상한과 구분합니다. 이벤트 대기열은 2,048개이며 초과는 실패입니다. 소유권 등록 잠금은 1초, Windows 감시 실행기는 3초, 감시 시작 후 준비 대기는 약 4.5초입니다. 중복 준비가 기존 준비를 기다릴 때는 Git 조회 중인 시간을 포함해 최대 9초이며, 통신은 수신 간격이 아닌 전체 요청별 3.5초, probe는 1.5초, Git 분류는 1초 제한입니다. 연속 이벤트 처리와 Stop 확인에도 유한 대기 제한을 두어 백그라운드 ignored 이벤트가 종료를 계속 붙잡지 않게 합니다. 셸·Node 시작과 감시 준비 비용은 남습니다.

상태는 OS 임시 폴더의 `ai-setting-code-quality-review/` 아래에 요청별로 저장합니다. 경로·수정 여부·검토 상태·프로세스 정보와 로컬 통신 인증정보를 담고 원문·프롬프트·프로젝트 파일 해시는 저장하지 않습니다. 기존 실패 사유와 허용 목록의 OS 오류 코드(`EACCES`, `EPERM` 등)를 보존하며 원문 오류 메시지는 기록하지 않습니다. 상태 파일은 비공개로 취급하고 내용을 로그에 출력하지 마세요.

새 감시 준비 시 마지막 정리 완료 후 1시간이 지났으면 디렉터리 항목을 최대 5,000개까지 확인하여 7일 지난 종료 기록과 그 owner 파일, 저장용 UUID 임시 파일을 정리합니다. 완료 시각은 `cleanup-completed.json`에 저장하며 누락·손상·미래 시각이면 정리를 다시 수행합니다. 정리 실패는 완료 시각을 갱신하지 않습니다. 동시에 시작한 요청은 정리가 겹칠 수 있습니다. 현재 요청·owner의 복구 대상과 활성·판단 불가 상태는 보존합니다. 원본 기록이 사라진 owner도 유실 감지·감시 종료용 복구 정보이므로 자동 삭제하지 않아 7일 넘게 남을 수 있습니다. 저장 실패 시 해당 임시 파일은 즉시 삭제를 시도하며 실패하면 이후 정리 대상으로 남습니다. 보존 기간이 지나 삭제된 종료 요청의 예산·실패 기록까지 복원할 수는 없습니다.

응답 마지막 줄의 상태로 다음 동작을 결정합니다.

- `[code-quality-review:revised]`: 이번 회차에서 수정·검증했으므로 다음 Stop에서 새 검토를 요청합니다.
- `[code-quality-review:clean]`: 수정 없는 검토에서 미해결 문제가 없고 필요한 검증이 충족됐으므로 종료합니다.
- `[code-quality-review:skipped]`: 비적용 작업으로 종료합니다. 검토 통과를 뜻하지 않습니다.
- `[code-quality-review:blocked]`: 답변·승인 필요, 검증 실패·실행 불가 등 사유를 보고하고 종료합니다. 검토 통과를 뜻하지 않습니다.

변경이 확인된 첫 응답의 종료 표식으로 검토를 생략할 수 없습니다. 검토 이후에는 코드 블록 밖의 마지막 독립 줄에 있는 종료 표식만 인정합니다. 상위 지침에 따른 후행 메모리 출처 블록(`<oai-mem-citation>`)은 정해진 `citation_entries`·`rollout_ids` 형식일 때 하나만 분리한 뒤 본문의 마지막 표식을 판별합니다. 임의의 후행 설명이나 태그는 허용하지 않습니다. 닫히지 않은 백틱·물결표 코드 블록 안의 표식이나 표식 누락·revised는 다시 검토를 요청합니다. 자동 검토 프롬프트는 사용자 요청당 최대 5회입니다. 감시 프로세스가 횟수 확인·증가·저장을 직렬로 처리하고 저장 성공을 확인한 경우에만 허가하므로 동시 Stop도 예산을 초과하지 않습니다. 다섯 번째 검토에서 받은 유효한 종료 표식은 인정합니다. 상한에도 종료를 확인하지 못하면 검토 미완료 경고를 남기고 추가 모델 프롬프트 없이 종료하며, 이를 clean으로 바꾸지 않습니다. 이 상한은 훅의 자동 재요청을 제한하며 한 번의 모델 응답 내부 작업 횟수까지 제어하지는 않습니다. 검토·수정·검증이 반복될수록 시간과 모델 사용량이 늘어납니다. 사용자가 중단할 수 있습니다. 다른 Stop 훅의 반복까지 제어하지는 않습니다.

인용문에 이어지는 문단은 줄 앞에 `>`가 없어도 인용문 안에 포함될 수 있으므로 그 안의 종료 표식은 인정하지 않습니다. 인용문 뒤에 빈 줄을 두면 종료 표식을 인용문 밖에 쓸 수 있습니다. 같은 인용문·목록 안에서 밑줄 제목이 완성된 뒤의 독립 종료 표식은 빈 줄 없이도 인정합니다.

Antigravity는 `fullyIdle: true`이고 정상 종료 사유인 `model_stop` 또는 기존 버전의 `NO_TOOL_CALL`일 때만 검토합니다. 백그라운드 작업이 남았거나 오류·취소·실행 제한으로 종료하면 강제로 재개하지 않습니다. 대화 기록에서 현재 `USER_INPUT/USER_EXPLICIT` 이후 이 훅의 요청 표식을 담은 `SYSTEM_MESSAGE/SYSTEM`과 마지막 `PLANNER_RESPONSE/MODEL`을 확인합니다. 이 기록 형식은 공식 입력 필드처럼 안정성이 보장된 규약이 아니므로 앱 버전이 바뀌면 실제 기록과 반복 종료를 다시 검증해야 합니다.

Antigravity 대화 기록은 작은 청크로 순차 읽고 현재 턴 판별에 필요한 상태만 유지합니다. 긴 줄은 마지막 조각까지 모아 한 번 합쳐 해석하며, 이미 읽은 부분을 청크마다 다시 검색하지 않습니다. 이전 기록의 JSON 검증과 빈 줄을 제외한 사용자 입력 위치에 따른 턴 식별은 유지합니다. 기록이 손상되거나 읽기 시작 때 확인한 크기보다 일찍 파일 끝에 도달하면 검토 미완료 경고를 남기며, 앞서 읽은 완료 표식으로 종료하지 않습니다.

## 검토 범위와 한계

상세 기준은 [REVIEW.md](REVIEW.md) 한곳에서 관리합니다. 이번 요청의 변경과 필요한 관련 코드만 검토하며 기존 사용자 작업을 보존합니다.

공통 규칙을 추가하거나 변경하면 새 구현의 기존 기능 재사용 여부와 기존 개별 구현의 중복·충돌을 양방향으로 대조하고 판단 근거를 보고합니다.

검토자는 편집·실행 내역, 현재 파일 목록, Git status와 diff로 이번 작업의 산출물 전체를 대조합니다. 새 문서와 문구, 미추적·ignored 작업용 파일, 일회성 테스트·진단 스크립트, 백업·전달 사본의 현재 용도를 확인합니다. 제거한 항목과 유지한 후보의 경로·이유를 최종 응답에 짧게 남기며, 검토 증명용 Markdown 보고서는 새로 만들지 않습니다. 필요한 회귀 테스트·운영 문서·복구 사본은 보존합니다. 작업 전 상태나 변경 소유 범위를 확정할 수 없으면 한계를 보고하고 임의로 정리하지 않습니다.

훅은 감지 여부와 모델의 종료 표식을 검사하며, 작업 전 파일 원문을 백업하거나 검토 근거의 충분성을 자동 판정하지 않습니다. 의미상 미사용 코드·중복 문구·불필요한 테스트의 판정은 같은 대화의 모델이 수행합니다. 자동 테스트는 감지·재요청·종료 동작을 검증하며 모델이 모든 잔여물을 찾는다는 보장은 아닙니다. 일반 ignored 파일이나 감시 밖의 사본은 자동 감지가 누락될 수 있으므로 검토자가 이번 실행 내역의 경로도 확인합니다.

답변·승인 대기 또는 중단 요청은 적용 대상 변경 전이면 `skipped`, 이미 변경했다면 `blocked`이며, 중단 요청 시 추가 검토·수정을 진행하지 않습니다. `AGENTS.md`의 원래 승인·업무 규칙을 유지하며, 훅이 새 권한을 부여하지 않습니다.

검토는 같은 대화의 AI 판단입니다. 특정 모델이나 새 서브에이전트를 훅 자체가 고정 호출하지 않으며, 원래 사용자가 지정한 모델·리뷰어 조건을 따르도록 지시합니다. 상태 표식은 모델의 자기 보고이므로 모든 버그의 발견이나 실제 테스트 결과를 훅 자체가 독립적으로 증명하지는 않습니다.

OS의 파일 감시는 네트워크 파일시스템·가상화 환경에서 불안정할 수 있으며 보고되지 않은 이벤트 유실까지 검출한다고 보장하지 않습니다. 이 환경은 별도 검증이 필요합니다. 입력·지침·대화 기록을 읽거나 해석하지 못한 경우에도 자동 검토 완료로 간주하지 않습니다. Codex는 `systemMessage` 경고 JSON, Antigravity는 stderr 경고와 빈 JSON을 반환합니다. 클라이언트에 따라 경고가 출력에 나타나지 않을 수 있습니다. Codex CLI 0.160.0의 `--no-daemon exec --json`에서는 공식 `systemMessage`의 출력 누락을 확인했습니다. 경고 JSON 반환과 실제 화면·CLI 표시는 별도이며, 표시를 확인했다고 주장하지 않습니다. 문제가 의심되면 훅 실행 로그와 비밀 필드를 제외한 실패 상태를 함께 확인합니다. Node나 훅 자체를 시작하지 못하는 오류도 별도로 확인해야 합니다.

## 설치·검증·해제

- [Windows 설정](README.windows.md)
- [macOS 설정](README.macos.md)

실행 코드는 Codex의 `~/.codex/hooks/code-quality-review/`와 Antigravity의 `~/.gemini/config/hooks/code-quality-review/`에 공통 파일과 해당 도구 어댑터를 복사합니다. 운영체제별 안내의 설치본 경로에서 설정을 생성하며 저장소 원본을 직접 등록하지 않습니다. 원본 갱신 후에는 다시 복사·검증해야 합니다.

기존 전역 설정 전체를 백업하고, 생성한 설정을 기존 훅·이벤트·핸들러를 보존하며 병합합니다. 전역과 프로젝트 양쪽에 같은 훅을 중복 등록하지 않습니다. 저장소를 받거나 이 파일을 수정하는 것만으로 전역 등록이 변경되지는 않습니다.

기존 Codex 루트 스크립트는 제거했습니다. 이전 경로를 등록한 환경은 운영체제별 안내에 따라 복사한 Codex 어댑터의 `--print-config`로 설정을 다시 생성해 해당 Stop 핸들러를 갱신하고 검토·신뢰 등록합니다.

코드를 변경한 경우 다음 자동 테스트를 실행합니다. 운영체제별 명령 실행과 실제 대화 확인은 각 안내를 따릅니다.

```sh
node --test --test-concurrency=1 hooks/code-quality-review/review-status.test.mjs hooks/code-quality-review/review-changes.test.mjs hooks/code-quality-review/codex/codex-code-quality-review.test.mjs hooks/code-quality-review/gemini/gemini-code-quality-review.test.mjs
```

테스트 파일은 순차 실행해 감시 프로세스 준비와 Git 조회의 짧은 제한에 병렬 테스트 부하가 겹치지 않게 합니다. 종료 표식과 코드 펜스의 전체 조합은 공통 판별 함수를 직접 검사합니다. Codex·Antigravity의 실제 훅 테스트도 열린 펜스에서 재검토하고 닫힌 펜스 뒤에서 종료하는지 세 종료 상태별로 확인합니다.

해제할 때는 Codex의 해당 UserPromptSubmit·Stop 핸들러 또는 Antigravity의 `ai-setting-code-quality-review` 키만 비활성화하거나 제거합니다. 시크릿 검사 등 다른 훅과 기존 기능 설정을 유지합니다. 이미 비활성화한 설정을 갱신할 때는 해당 상태도 보존합니다.

공식 계약과 감시 한계: [Node.js fs.watch](https://nodejs.org/api/fs.html#fswatchfilename-options-listener), [Codex Hooks](https://learn.chatgpt.com/docs/hooks), [Antigravity Hooks](https://antigravity.google/docs/hooks).
