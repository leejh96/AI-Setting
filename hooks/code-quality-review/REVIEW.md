완료 전 코드 품질 검토 지침입니다. 새 작업·권한·승인을 부여하지 않으며, 원래 사용자 요청과 이후 정정, 적용 지침과 승인 범위를 유지합니다.

## 1. 적용 여부와 검토 범위

이 지침을 받을 때마다 새 검토 회차를 수행하세요. 이번 요청이 구현·수정이고 직접 또는 허용된 서브에이전트를 통해 실제 코드·스크립트·동작 설정을 변경한 경우에 적용합니다. 훅의 직전 응답만이 아니라 원래 요청과 전체 작업 내역으로 판단하며, 앞 회차에서 변경을 마쳤다는 이유로 제외하지 마세요. 적용 여부 확인을 위해 저장소 전체를 검색하지 마세요.

설명·조사·읽기 전용 리뷰·변경 없는 작업·문서만 작성한 작업·사용자 답변이나 승인 대기·중단 요청은 검토·수정 없이 기존 결과를 간결히 보고하고 종료합니다. 적용 전 비대상은 `skipped`, 적용 대상이지만 진행할 수 없는 경우는 4절의 `blocked`를 따릅니다.

검토 대상은 이번 요청으로 만든 변경과 이해에 필요한 관련 코드입니다.

- 매회 변경한 주요 파일의 현재 내용을 실제로 읽으세요. 이전 읽기 결과나 완료 보고로 대신하지 마세요. 현재 내용이 기존 검증 대상과 달라졌다면 영향에 맞는 검증을 다시 수행하세요.
- 작업 전 상태와 실제 diff를 기준으로 기존 사용자 변경·다른 요청의 변경·무관한 파일을 구분하고 보존하세요. 이미 커밋했거나 여러 저장소를 수정했다면 해당 파일과 커밋도 확인하세요.
- git diff 전체를 이번 요청의 변경이라고 가정하지 마세요. 변경의 소유 범위가 불명확하면 임의로 되돌리거나 정리하지 마세요.

## 2. 점검 항목

다음 항목을 실제 코드·요구사항·기존 계약에 근거해 확인하세요. 반드시 문제를 찾아야 하는 것은 아닙니다.

1. 요청 충족: 합의한 요구사항 누락이나 요청 밖 기능이 없는지, 정상 흐름과 중요한 권한·입력·실패 분기, 데이터의 최종 상태가 요구사항에 맞는지 확인하세요. 기획·업무 규칙이 미확정이면 임의로 채우지 말고 필요한 질문을 남기세요. 이번 작업 중 요구사항 변경으로 불필요해진 코드·테스트·설정이 남았는지도 확인하고, 승인 범위 안에서 현재 요구사항·참조·계약상 더 이상 필요 없다고 확인된 부분만 제거하거나 수정하세요.
2. AI 슬롭: 코드 내용을 반복하는 불필요한 주석, 의미 없는 변수·래퍼, 오류를 숨기는 catch·임시 우회, 근거 없는 기본값·방어 처리, 미사용 코드가 이번 변경에 추가됐는지 확인하세요. 필요한 입력 검증과 기존 정책에 따른 예외 처리는 유지하세요.
3. 과잉 설계: 현재 요구에 필요 없는 추상화 계층·디자인 패턴·설정·의존성, 가정한 미래 요구를 위한 확장 구조, 무관한 리팩터링을 제거할 근거가 있는지 확인하세요. 코드 줄 수보다 요구 충족·가독성·기존 구조와의 일관성을 우선하세요.
4. 중복 구현: 같은 책임과 업무 규칙의 기존 코드·공통 모듈·표준 기능으로 해결할 수 있었는지 확인하세요. 모양만 비슷하거나 변경 이유가 다른 코드를 억지로 합치지 말고, 예상 재사용만을 위한 공통화나 더 큰 변경을 만들지 마세요.
5. 보안: 이번 변경과 필요한 관련 코드·테스트·설정에서 인증·권한 누락, 사용자 입력 처리, 인젝션·XSS·SSRF·경로 조작 등 해당 변경과 관련된 취약점을 확인하세요. 실제 인증정보의 하드코딩과 민감정보의 불필요한 로그·오류·응답 노출도 점검하세요. 발생 조건과 실제 코드 흐름을 근거로 판단하고, 근거 없이 취약점으로 단정하거나 전체 저장소 보안 감사로 확대하지 마세요. 발견한 실제 민감정보 값은 출력하거나 복사하지 말고 위치와 유형만 보고하세요. 가상 테스트 값과 정상적인 인증정보 참조를 실제 시크릿 노출로 단정하지 마세요.
6. 버전 호환성: 이번 변경에서 사용하거나 변경한 문법·API·설정·의존성이 프로젝트의 실제 런타임·프레임워크·의존성 버전과 명시된 지원 버전 범위에서 호환되는지 확인하세요. 버전은 manifest·lockfile·배포 설정 등 프로젝트 근거로 확인하고, 필요하면 해당 버전의 공식 문서를 참고하세요. 이번 변경에 영향을 받는 부분만 확인하며, 필요한 호환성을 확인하지 못한 부분은 미확인으로 보고하세요. 해결을 위해 버전 업그레이드나 지원 범위를 임의로 변경하지 마세요.

## 3. 문제 수정과 검증

실제 문제가 확인된 경우에만 이번 요청의 승인 범위 안에서 원인에 맞게 최소 수정하세요. 취향이나 막연한 가능성만으로 다시 쓰거나 변경을 반복하지 마세요.

새 업무 정책·추가 비용·운영 변경·권한이 필요한 작업은 기존 승인 원칙을 따릅니다. 검토를 위해 commit·push·배포·외부 메시지 전송을 새로 수행하지 마세요. 서브에이전트는 원래 사용자 요청이나 적용 지침이 허용한 범위에서 활용하고, 모델·매회 새 리뷰어 등 명시된 조건을 유지하세요.

수정했다면 영향에 맞는 필요한 검증을 실행하고, 최종 diff에서 문제 해소와 수정의 영향을 확인하세요. 이미 유효한 검증을 이유 없이 반복하거나 사소한 문구 변경에 테스트를 새로 만들지 마세요. 해결하지 못한 문제·실패한 검증·미실행 검증은 숨기거나 전체 완료로 표현하지 마세요.

## 4. 반복·종료 조건과 상태 표식

각 회차의 응답은 검토로 바꾼 핵심 사항, 실제 검증 범위와 남은 한계를 짧게 설명하고, 마지막 줄에 다음 상태 표식 중 하나만 정확히 쓰세요. 표식은 코드 블록이나 인용문으로 감싸지 마세요.

- `[code-quality-review:revised]`: 이번 회차에서 수정하고 필요한 검증을 수행했습니다. 최종 완료로 보고하지 마세요. 다음 Stop이 새 회차를 요청하므로 수정된 현재 코드와 관련 범위의 다른 실제 문제를 재검토합니다.
- `[code-quality-review:clean]`: 이번 회차에서는 수정하지 않았고, 합의한 범위를 실제로 검토한 결과 미해결 문제가 없으며 필요한 검증이 충족됐습니다. 원래 요청의 최종 결과를 보고하고 종료합니다. 검사하지 않은 항목을 통과했다고 말하지 마세요.
- `[code-quality-review:skipped]`: 위의 비적용 작업입니다. 원래 결과나 필요한 질문을 보고하고 종료합니다. 검토 통과를 뜻하지 않습니다.
- `[code-quality-review:blocked]`: 적용 대상이지만 해결하지 못한 문제, 필요한 검증의 실패·실행 불가, 추가 답변·승인 필요 또는 중단 요청 때문에 진행할 수 없습니다. 미완료 사유와 필요한 조치를 보고하고 종료합니다. 검토 통과를 뜻하지 않습니다. 진행 가능한 승인 범위의 수정·검증은 먼저 수행하세요.

표식이 없거나 `revised`이면 다음 검토를 요청합니다. 이번 회차에서 수정했다면 검증에 통과해도 `clean`으로 종료하지 마세요. 수정 후에도 막힌 문제가 남으면 `blocked`를 우선하며, 횟수만으로 `clean`을 선언하지 마세요.
