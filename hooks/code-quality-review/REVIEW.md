완료 전 코드 품질 검토 훅입니다. 이 메시지는 검토 절차만 요청하며 새 작업·권한·승인을 부여하지 않습니다. 원래 사용자 요청, 이후 정정, 적용 지침과 승인 범위를 유지하세요.

이 메시지를 받을 때마다 새 검토 회차를 수행하세요. 먼저 대화 맥락으로 적용 여부를 판단하세요. 이번 요청이 구현·수정이고 직접 또는 허용된 서브에이전트를 통해 실제 코드·스크립트·동작 설정을 변경한 경우에만 아래 검토를 수행하세요. 설명·조사·읽기 전용 리뷰, 변경 없는 작업, 문서만 작성한 작업, 사용자 답변·승인을 기다리는 상황, 사용자가 중단을 요청한 상황은 검토·수정 없이 기존 결과를 간결하게 보고하고 종료하세요. 적용 여부 확인을 위해 저장소 전체를 검색하지 마세요. 적용 여부는 훅의 직전 응답만이 아니라 원래 요청과 전체 작업 내역으로 판단하며, 앞 회차에서 변경을 마쳤다는 이유로 검토 대상에서 제외하지 마세요.

검토 대상은 이번 요청으로 만든 변경과 그 변경을 이해하는 데 필요한 관련 코드입니다. 적용 대상이면 이번 요청으로 변경한 주요 파일의 현재 내용을 검토 시점에 실제로 읽으세요. 이전 읽기 결과나 완료 보고만으로 이번 검토를 대신하지 마세요. 현재 내용이 기존 검증 대상과 달라졌다면 영향에 맞는 검증을 다시 수행하세요. 작업 전 상태와 실제 diff를 기준으로 기존 사용자 변경, 다른 요청의 변경, 무관한 파일을 구분하고 보존하세요. 이미 커밋했거나 여러 저장소를 수정했다면 해당 파일과 커밋도 확인하세요. git diff 전체를 이번 요청의 변경이라고 가정하지 마세요. 변경의 소유 범위가 불명확하면 임의로 되돌리거나 정리하지 마세요.

다음 항목을 실제 코드·요구사항·기존 계약에 근거해 확인하세요. 반드시 문제를 찾아야 하는 것은 아닙니다.

1. 요청 충족: 합의한 요구사항 누락이나 요청 밖 기능이 없는지, 정상 흐름과 중요한 권한·입력·실패 분기, 데이터의 최종 상태가 요구사항에 맞는지 확인하세요. 기획·업무 규칙이 미확정이면 임의로 채우지 말고 필요한 질문을 남기세요. 이번 작업 중 요구사항 변경으로 불필요해진 코드·테스트·설정이 남았는지도 확인하고, 승인 범위 안에서 현재 요구사항·참조·계약상 더 이상 필요 없다고 확인된 부분만 제거하거나 수정하세요.
2. AI 슬롭: 코드 내용을 반복하는 불필요한 주석, 의미 없는 변수·래퍼, 오류를 숨기는 catch·임시 우회, 근거 없는 기본값·방어 처리, 미사용 코드가 이번 변경에 추가됐는지 확인하세요. 필요한 입력 검증과 기존 정책에 따른 예외 처리는 유지하세요.
3. 과잉 설계: 현재 요구에 필요 없는 추상화 계층·디자인 패턴·설정·의존성, 가정한 미래 요구를 위한 확장 구조, 무관한 리팩터링을 제거할 근거가 있는지 확인하세요. 코드 줄 수보다 요구 충족·가독성·기존 구조와의 일관성을 우선하세요.
4. 중복 구현: 같은 책임과 업무 규칙의 기존 코드·공통 모듈·표준 기능으로 해결할 수 있었는지 확인하세요. 모양만 비슷하거나 변경 이유가 다른 코드를 억지로 합치지 말고, 예상 재사용만을 위한 공통화나 더 큰 변경을 만들지 마세요.

실제 문제가 확인된 경우에만 이번 요청의 승인 범위 안에서 원인에 맞게 최소 수정하세요. 취향이나 막연한 가능성만으로 다시 쓰지 마세요. 새 업무 정책, 추가 비용·운영 변경, 권한이 필요한 작업은 기존 승인 원칙을 따르며 이 훅을 승인으로 해석하지 마세요. 검토를 위해 commit·push·배포·외부 메시지 전송을 새로 수행하지 마세요. 서브에이전트는 원래 사용자 요청이나 적용 지침이 허용한 범위에서 활용하고, 모델·매회 새 리뷰어 등 명시된 조건을 유지하세요.

수정한 경우에는 영향에 맞는 필요한 검증을 실행하고, 최종 diff에서 지적한 문제가 해소됐는지와 수정의 영향을 확인하세요. 이미 유효하게 수행한 검증을 이유 없이 반복하거나 사소한 문구 변경에 테스트를 새로 만들지 마세요. 이번 회차에서 수정했다면 검증 후에도 통과로 선언하지 말고 아래 revised 상태로 회차를 마치세요. 훅이 다시 호출하여 수정된 현재 코드와 관련 범위의 다른 실제 문제를 새 회차에서 검토하게 합니다. 수정 없는 검토 회차에서 미해결 문제가 없고 필요한 검증이 충족될 때까지 검토→수정·검증→재검토를 반복하세요. 같은 범위의 취향 문제로 변경을 반복하지 마세요. 해결하지 못한 문제·실패한 검증·미실행 검증은 숨기거나 전체 완료로 표현하지 마세요.

각 회차의 응답은 검토로 바꾼 핵심 사항, 실제 검증 범위와 남은 한계를 짧게 설명하고, 마지막 줄에 다음 상태 표식 중 하나만 정확히 쓰세요. 표식은 코드 블록이나 인용문으로 감싸지 마세요.

- `[code-quality-review:revised]`: 이번 회차에서 수정하고 필요한 검증을 수행했습니다. 아직 최종 완료로 보고하지 마세요. 다음 Stop에서 훅이 새 검토 회차를 요청합니다.
- `[code-quality-review:clean]`: 이번 회차에서는 수정하지 않았고, 합의한 범위를 실제로 검토한 결과 미해결 문제가 없으며 필요한 검증이 충족됐습니다. 원래 요청의 최종 결과를 보고하고 종료합니다. 검사하지 않은 항목을 통과했다고 말하지 마세요.
- `[code-quality-review:skipped]`: 위의 비적용 작업입니다. 원래 결과나 필요한 질문을 보고하고 종료합니다. 검토 통과를 뜻하지 않습니다.
- `[code-quality-review:blocked]`: 적용 대상이지만 해결하지 못한 문제, 필요한 검증의 실패·실행 불가, 추가 답변·승인 필요 또는 중단 요청 때문에 진행할 수 없습니다. 미완료 사유와 필요한 조치를 보고하고 종료합니다. 검토 통과를 뜻하지 않습니다. 진행 가능한 승인 범위의 수정·검증은 먼저 수행하세요.

표식이 없거나 revised이면 훅은 다음 검토를 요청합니다. 반복 횟수만으로 clean을 선언하지 마세요. 수정 후에도 막힌 문제가 남으면 revised보다 blocked를 우선하여 무의미한 반복을 멈추세요.
