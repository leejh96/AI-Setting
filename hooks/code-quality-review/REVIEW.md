완료 전 코드 품질 검토 지침입니다. 새 작업·권한·승인을 부여하지 않으며, 원래 사용자 요청과 이후 정정, 적용 지침과 승인 범위를 유지합니다.

## 1. 적용 여부와 검토 범위

이 지침을 받을 때마다 새 검토 회차를 수행하세요. 원래 요청과 전체 작업 내역에서 직접 또는 허용된 서브에이전트를 통해 생성·수정·삭제한 코드·스크립트·동작 설정·문서·테스트·작업용 파일이 대상입니다. 문서만 변경했거나 앞 회차에서 변경을 마친 경우도 포함합니다. 적용 여부 확인을 위해 저장소 전체를 검색하지 마세요.

훅은 파일 변경 이벤트로 검토를 시작하며 같은 내용 저장·수정 후 원복도 기록할 수 있습니다. 정상 감시에서 수정 기록이 없으면 모델을 재개하지 않습니다. 감시 실패는 검토 통과가 아니며, 훅이 미완료 경고를 남기고 추가 모델 응답 없이 종료합니다.

실제 파일 변경이 없는 설명·조사·읽기 전용 리뷰는 추가 검토·수정 없이 `skipped`로 종료합니다. 구현·수정에 필요한 답변·승인 대기나 중단 요청도 적용 대상인 변경을 수행하기 전이면 `skipped`입니다. 이번 요청에서 이미 적용 대상인 변경을 수행했다면 이후 답변·승인 대기나 중단 요청은 `blocked`로 종료하고 미완료 범위를 보고합니다. 중단 요청 시에는 추가 검토·수정을 진행하지 않습니다.

검토 대상은 이번 요청으로 만든 변경·산출물 전체와 이해에 필요한 관련 코드·문서입니다. 새 프로젝트나 기능 전체를 만든 요청이면 그 요청에서 만든 파일 전체가 대상입니다. 기존 프로젝트의 일부 수정은 무관한 전체 코드베이스 정리로 확대하지 않습니다.

- 매회 변경한 주요 파일의 현재 내용을 실제로 읽으세요. 이전 읽기 결과나 완료 보고로 대신하지 마세요. 현재 내용이 기존 검증 대상과 달라졌다면 영향에 맞는 검증을 다시 수행하세요. 이번 대화에서 현재 변경에 대한 검증 성공이 확인되고, 이후 검증에 영향을 주는 변경이나 새로운 실패 증거가 없다면 동일 검증을 반복하지 마세요.
- 작업 전 상태와 실제 diff, 이번 요청의 편집·도구 실행 내역을 대조해 기존 사용자 변경·다른 요청의 변경·무관한 파일을 구분하고 보존하세요. 이미 커밋했거나 여러 저장소를 수정했다면 해당 파일과 커밋도 확인하세요. 미추적 파일은 일반적인 git diff에 나오지 않으므로 관련 파일의 현재 내용을 직접 확인하세요.
- 첫 회차에는 편집·터미널 실행 내역과 현재 파일 목록을 대조해 이번 작업의 산출물을 빠짐없이 확인하세요. Git 프로젝트는 `git status --short --untracked-files=all`과 diff를 함께 보고, Git이 없으면 작업한 디렉터리의 파일 목록을 확인하세요. 작업 중 만든 ignored 경로·저장소 밖 임시 경로·전달본·백업은 실행 내역에서 경로를 찾아 따로 확인하세요. 대용량 데이터나 비밀 파일은 내용을 출력하지 말고 경로·용도·크기 등 필요한 메타데이터로 판단하세요. 이후 회차에는 이 목록과 추가 변경을 대조하세요. 주요 소스 몇 개를 읽거나 테스트가 통과했다는 이유로 산출물 점검을 생략하지 마세요.
- 훅의 변경 감시는 작업 전 파일 원문을 보관하는 백업이 아닙니다. 작업 전 상태를 확보하지 못했다면 확인 가능한 편집 내역 등으로 변경 범위를 판단하고, 구분할 수 없는 부분은 검토 한계로 보고하세요. git diff 전체를 이번 요청의 변경이라고 가정하거나 소유 범위가 불명확한 코드를 임의로 되돌리거나 정리하지 마세요. 그 불명확성이 요청 충족이나 필수 검증 판단을 막으면 `blocked`로 보고하세요.

## 2. 점검 항목

먼저 아래 산출물 점검을 수행하고, 이어서 변경에 해당하는 코드 품질 항목을 확인하세요. 문서만 변경했다면 문서 내용·참조·중복·잔여물과 해당 검증을 확인하며 무관한 코드 검사를 강제하지 않습니다. 반드시 문제를 찾아야 하는 것은 아닙니다.

### 산출물과 잔여물 점검

- **코드·설정:** 새 진입점·함수·옵션이 현재 요구와 실제 호출·등록 경로에 연결되는지 확인하세요. 요구 변경으로 폐기된 기능·구버전 호환 분기·사용처 없는 구현·일회성 진단 코드를 찾으세요. 테스트에서만 호출된다는 사실은 운영 코드의 사용 근거가 아닙니다. 동적 등록·외부 계약·공개 API가 있으면 참조 검색 결과만으로 삭제하지 마세요.
- **Markdown과 문구:** 독자가 현재 수행할 행동과 확인할 결과에 필요한지 확인하세요. 요청하지 않은 작업 일지·검토 통과 보고서·정리 내역 문서, 기존 안내와 중복되는 문서, 폐기된 기능의 설명·명령·완료 주장·임시 주석은 정리하세요. 파일 전체뿐 아니라 남은 문단과 예시도 확인하세요. 현재 운영 절차·설계 결정·외부 계약·조회 근거로 필요한 문서는 유지하세요. 내부 참조가 있다는 사실만으로 불필요한 문서를 존치하지 말고 참조의 목적도 확인하세요.
- **테스트·스크립트:** 실제 요구와 중요한 실패·회귀를 검증하는 테스트는 유지하세요. 일회성 확인·샘플 실행·디버그 코드, 삭제한 기능의 테스트, 구현을 그대로 복제하거나 자기 자신만 확인하는 테스트, 같은 조건·결과를 중복 검증하는 테스트는 현재 목적을 확인해 정리하세요. 파일명에 test가 있다는 이유만으로 삭제하거나, 테스트가 있다는 이유만으로 불필요한 기능을 보존하지 마세요.
- **백업·임시·전달 사본:** 이번 작업에서 만든 백업·임시 파일·중복 압축본·구버전 산출물의 최종 상태를 확인하세요. 성공 후 용도가 끝난 작업용 사본은 승인 범위에서 정리하세요. 실패 복구·원본 보존·사용자가 요청한 전달·보관에 필요한 사본은 유지하고 이유를 남기세요. ignored 파일도 제외하지 마세요. 실제 필요와 소유 범위를 확인하지 못한 파일을 이름만으로 삭제하거나 원본 데이터를 정리 대상으로 취급하지 마세요.

정리했다면 남은 호출·설정·문서 링크·패키징 목록·테스트 참조를 확인하세요. 검토 결과를 증명하기 위한 새 Markdown 보고서·테스트 스크립트·백업을 추가하지 마세요. 필요한 근거는 최종 응답에 짧게 남기세요.

### 변경에 해당하는 코드 품질 점검

1. 요청 충족: 합의한 요구사항 누락이나 요청 밖 기능이 없는지, 정상 흐름과 중요한 권한·입력·실패 분기, 데이터의 최종 상태가 요구사항에 맞는지 확인하세요. 기획·업무 규칙이 미확정이면 임의로 채우지 말고 필요한 질문을 남기세요. 이번 작업 중 요구사항 변경으로 불필요해진 코드·테스트·설정이 남았는지도 확인하고, 승인 범위 안에서 현재 요구사항·참조·계약상 더 이상 필요 없다고 확인된 부분만 제거하거나 수정하세요.
2. AI 슬롭: 코드 내용을 반복하는 불필요한 주석, 의미 없는 변수·래퍼, 오류를 숨기는 catch·임시 우회, 근거 없는 기본값·방어 처리, 미사용 코드가 이번 변경에 추가됐는지 확인하세요. 필요한 입력 검증과 기존 정책에 따른 예외 처리는 유지하세요.
3. 과잉 설계: 현재 요구에 필요 없는 추상화 계층·디자인 패턴·설정·의존성, 가정한 미래 요구를 위한 확장 구조, 무관한 리팩터링을 제거할 근거가 있는지 확인하세요. 코드 줄 수보다 요구 충족·가독성·기존 구조와의 일관성을 우선하세요.
4. 중복 구현: 새 구현을 같은 책임과 업무 규칙의 기존 코드·공통 모듈·표준 기능으로 해결할 수 있었는지 확인하세요. 반대로 공통 규칙·유틸리티·기본 동작을 추가하거나 변경했다면 영향을 받는 기존 사용처를 검색해 새 규칙으로 중복되거나 충돌하게 된 개별 구현·설정·스타일도 대조하세요. 기존 동작을 유지하는 데 필요한 예외와 정리 가능한 중복을 구분하고, 제거 여부는 실제 참조·적용 순서·계약을 근거로 판단하세요. 모양만 비슷하거나 변경 이유가 다른 코드를 억지로 합치지 말고, 예상 재사용만을 위한 공통화나 더 큰 변경을 만들지 마세요.
5. 보안: 이번 변경과 필요한 관련 코드·테스트·설정에서 인증·권한 누락, 사용자 입력 처리, 인젝션·XSS·SSRF·경로 조작 등 해당 변경과 관련된 취약점을 확인하세요. 실제 인증정보의 하드코딩과 민감정보의 불필요한 로그·오류·응답 노출도 점검하세요. 발생 조건과 실제 코드 흐름을 근거로 판단하고, 근거 없이 취약점으로 단정하거나 전체 저장소 보안 감사로 확대하지 마세요. 발견한 실제 민감정보 값은 출력하거나 복사하지 말고 위치와 유형만 보고하세요. 가상 테스트 값과 정상적인 인증정보 참조를 실제 시크릿 노출로 단정하지 마세요.
6. 버전 호환성: 이번 변경에서 사용하거나 변경한 문법·API·설정·의존성이 프로젝트의 실제 런타임·프레임워크·의존성 버전과 명시된 지원 버전 범위에서 호환되는지 확인하세요. 버전은 manifest·lockfile·배포 설정 등 프로젝트 근거로 확인하고, 필요하면 해당 버전의 공식 문서를 참고하세요. 이번 변경에 영향을 받는 부분만 확인하며, 필요한 호환성을 확인하지 못한 부분은 미확인으로 보고하세요. 해결을 위해 버전 업그레이드나 지원 범위를 임의로 변경하지 마세요.

## 3. 문제 수정과 검증

실제 문제가 확인된 경우에만 이번 요청의 승인 범위 안에서 최소 수정하고 필요한 검증과 최종 diff로 문제 해소·영향을 확인하세요. 취향·막연한 가능성으로 변경을 반복하거나 사소한 문구 변경에 테스트를 새로 만들지 마세요.

새 업무 정책·추가 비용·운영 변경·권한은 기존 승인 원칙을 따릅니다. 검토를 위해 commit·push·배포·외부 메시지 전송을 새로 수행하지 마세요. 서브에이전트는 원래 요청이나 적용 지침이 허용한 범위와 모델·매회 새 리뷰어 등 명시된 조건을 유지하세요. 미해결·검증 실패·미실행은 다음 절의 종료 상태에 반영하세요.

## 4. 반복·종료 조건과 상태 표식

적용 대상인 각 검토 회차의 응답에는 검토한 주요 변경과 기존 구현을 대조한 대상·판단 근거, 수정 여부, 실제 검증 범위와 남은 한계를 필요한 항목만 짧게 설명하세요. 산출물 점검에서 제거한 항목과 유지한 후보의 실제 경로·이유를 보통 1~2문장으로 남기세요. 후보가 없었다면 확인한 파일 범위와 방법을 밝히세요. 파일마다 긴 목록이나 새 보고서 파일은 필요하지 않습니다. 산출물 목록·용도를 확인하지 않았거나 미해결 후보가 요청 충족을 막으면 `clean`으로 종료하지 마세요. 수정하지 않은 회차에도 실제로 확인한 근거를 남기고, 근거 없이 "문제 없음"이나 점검 항목별 통과 문구만 나열하지 마세요. 비적용 또는 중단 요청으로 검토하지 않은 경우에는 그 사유와 기존 결과만 보고하세요. 마지막 줄에는 다음 상태 표식 중 하나만 정확히 쓰세요. 표식은 코드 블록이나 인용문으로 감싸지 마세요.

상위 지침이 메모리 출처 블록(`<oai-mem-citation>`)을 응답 맨 끝에 요구하면, 상태 표식은 그 블록 직전 본문의 마지막 독립 줄에 둡니다. 판별기는 정해진 `citation_entries`·`rollout_ids` 형식의 후행 블록 하나만 분리하며, 다른 후행 설명이나 임의의 태그·코드 블록·인용문 안의 표식은 종료로 인정하지 않습니다.

수정 없는 `clean` 회차에서는 원래 요청의 최종 결과를 짧게 보고하고, 앞선 보고와 겹치는 작업 설명·점검 항목별 서술은 생략하세요. 이번 회차에 확인한 핵심 근거와 실제 검증·미확인 범위는 보통 1~2문장으로 압축하되, 중요한 한계를 숨기거나 이전 답변을 읽어야만 결과를 이해할 수 있게 만들지 마세요. 보고를 줄이는 것이 매회 현재 파일 확인과 필요한 검증을 생략하는 근거는 아닙니다.

- `[code-quality-review:revised]`: 이번 회차에서 수정하고 필요한 검증을 수행했습니다. 최종 완료로 보고하지 마세요. 다음 Stop이 남은 검토 예산 안에서 새 회차를 요청하므로 수정된 현재 코드와 관련 범위의 다른 실제 문제를 재검토합니다.
- `[code-quality-review:clean]`: 이번 회차에서는 수정하지 않았고, 합의한 범위를 실제로 검토한 결과 미해결 문제가 없으며 필요한 검증이 충족됐습니다. 원래 요청의 최종 결과를 보고하고 종료합니다. 검사하지 않은 항목을 통과했다고 말하지 마세요.
- `[code-quality-review:skipped]`: 위의 비적용 작업입니다. 원래 결과나 필요한 질문을 보고하고 종료합니다. 검토 통과를 뜻하지 않습니다.
- `[code-quality-review:blocked]`: 적용 대상이지만 해결하지 못한 문제, 필요한 검증의 실패·실행 불가, 추가 답변·승인 필요 또는 중단 요청 때문에 진행할 수 없습니다. 미완료 사유와 필요한 조치를 보고하고 종료합니다. 검토 통과를 뜻하지 않습니다. 중단 요청이 없다면 진행 가능한 승인 범위의 수정·검증은 먼저 수행하세요.

표식이 없거나 `revised`이면 남은 예산 안에서 다음 검토를 요청합니다. 자동 검토 재요청은 사용자 요청당 최대 5회입니다. 마지막 허용 회차의 유효한 종료 응답은 정상적으로 인정하며, 상한 이후에도 종료를 확인하지 못하면 훅은 검토 미완료 경고를 남기고 추가 재요청 없이 종료합니다. 상한을 검토 통과로 해석하지 마세요.

이번 회차에서 수정했다면 검증에 통과해도 `clean`으로 종료하지 마세요. 수정 후에도 막힌 문제가 남으면 `blocked`를 우선하며, 횟수만으로 `clean`을 선언하지 마세요.
