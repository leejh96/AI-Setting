완료 전 코드 품질 검토 훅입니다. 이 메시지는 검토 절차만 요청하며 새 작업·권한·승인을 부여하지 않습니다. 원래 사용자 요청, 이후 정정, 적용 지침과 승인 범위를 유지하세요.

먼저 대화 맥락으로 적용 여부를 판단하세요. 이번 요청이 구현·수정이고 직접 또는 허용된 서브에이전트를 통해 실제 코드·스크립트·동작 설정을 변경한 경우에만 아래 검토를 한 번 수행하세요. 설명·조사·읽기 전용 리뷰, 변경 없는 작업, 문서만 작성한 작업, 사용자 답변·승인을 기다리는 상황, 사용자가 중단을 요청한 상황은 검토·수정 없이 기존 결과를 간결하게 보고하고 종료하세요. 적용 여부 확인을 위해 저장소 전체를 검색하지 마세요.

검토 대상은 이번 요청으로 만든 변경과 그 변경을 이해하는 데 필요한 관련 코드입니다. 작업 전 상태와 실제 diff를 기준으로 기존 사용자 변경, 다른 요청의 변경, 무관한 파일을 구분하고 보존하세요. 이미 커밋했거나 여러 저장소를 수정했다면 해당 파일과 커밋도 확인하세요. git diff 전체를 이번 요청의 변경이라고 가정하지 마세요. 변경의 소유 범위가 불명확하면 임의로 되돌리거나 정리하지 마세요.

다음 항목을 실제 코드·요구사항·기존 계약에 근거해 확인하세요. 반드시 문제를 찾아야 하는 것은 아닙니다.

1. 요청 충족: 합의한 요구사항 누락이나 요청 밖 기능이 없는지, 정상 흐름과 중요한 권한·입력·실패 분기, 데이터의 최종 상태가 요구사항에 맞는지 확인하세요. 기획·업무 규칙이 미확정이면 임의로 채우지 말고 필요한 질문을 남기세요.
2. AI 슬롭: 코드 내용을 반복하는 불필요한 주석, 의미 없는 변수·래퍼, 오류를 숨기는 catch·임시 우회, 근거 없는 기본값·방어 처리, 미사용 코드가 이번 변경에 추가됐는지 확인하세요. 필요한 입력 검증과 기존 정책에 따른 예외 처리는 유지하세요.
3. 과잉 설계: 현재 요구에 필요 없는 추상화 계층·디자인 패턴·설정·의존성, 가정한 미래 요구를 위한 확장 구조, 무관한 리팩터링을 제거할 근거가 있는지 확인하세요. 코드 줄 수보다 요구 충족·가독성·기존 구조와의 일관성을 우선하세요.
4. 중복 구현: 같은 책임과 업무 규칙의 기존 코드·공통 모듈·표준 기능으로 해결할 수 있었는지 확인하세요. 모양만 비슷하거나 변경 이유가 다른 코드를 억지로 합치지 말고, 예상 재사용만을 위한 공통화나 더 큰 변경을 만들지 마세요.

실제 문제가 확인된 경우에만 이번 요청의 승인 범위 안에서 원인에 맞게 최소 수정하세요. 취향이나 막연한 가능성만으로 다시 쓰지 마세요. 새 업무 정책, 추가 비용·운영 변경, 권한이 필요한 작업은 기존 승인 원칙을 따르며 이 훅을 승인으로 해석하지 마세요. 검토를 위해 commit·push·배포·외부 메시지 전송을 새로 수행하지 마세요. 서브에이전트는 원래 사용자 요청이나 적용 지침이 허용한 범위에서 활용하세요.

수정한 경우에는 영향에 맞는 필요한 검증을 실행하고, 최종 diff에서 지적한 문제가 해소됐는지와 수정의 영향을 확인하세요. 이미 유효하게 수행한 검증을 이유 없이 반복하거나 사소한 문구 변경에 테스트를 새로 만들지 마세요. 같은 범위를 취향으로 재검토하며 반복하지 말고 이 한 번의 검토 안에서 마치세요. 해결하지 못한 문제·실패한 검증·미실행 검증은 숨기거나 전체 완료로 표현하지 마세요.
