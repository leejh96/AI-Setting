# Antigravity 워커

Codex가 작업 범위와 완료 조건을 정합니다. Antigravity는 작업 결과를 작업 폴더에 남깁니다. Codex가 결과 검토, 원본 반영, 임시 작업 폴더 정리를 맡습니다.

## 작업 전달

- Node.js 22 이상과 로그인된 Antigravity 명령줄 도구(CLI) `agy`가 필요합니다. `gemini-4-hydrogen-high`, `--effort high`, 대화형 시작 프롬프트(`-i`)와 워크스페이스 훅을 지원하는 버전을 사용합니다.
- 변경 작업은 가능한 경우 승인 범위 안에서 `prepare <original-worktree>`로 만든 별도 Git 워크트리에 위임합니다. 이 워크트리는 원본의 현재 커밋에서 시작합니다. Git이 필요 없는 일회성 작업 폴더는 인자 없이 `prepare`로 만듭니다. 이미 지정된 작업 경로를 사용할 때는 시작 전 상태를 확인합니다. 같은 경로에서 Codex와 워커가 동시에 편집하지 않습니다.
- 저장소 밖 UTF-8 파일에 목표, 절대 작업 경로, 수정 범위, 수용 조건, 검증 방법을 씁니다. 워커에 허용된 셸·MCP·브라우저와 리소스를 명시합니다. 초기 프롬프트는 실행 인자로 전달하므로 비밀값을 넣지 않고, Windows에서는 12,000자 이내로 작성합니다.
- 실행기는 `--dangerously-skip-permissions`와 `--sandbox` 옵션을 사용합니다. 해당 환경에서 터미널 샌드박스가 지원되는지 확인하고, 외부 전송·운영 데이터 변경·커밋·푸시·배포는 현재 사용자 승인 범위에 따릅니다. 브라우저 검증은 별도 요청에 허용된 브라우저 작업과 범위를 적습니다. Chrome 원격 디버깅 승인과 조직 정책은 각 환경에서 확인합니다.
- Codex의 실행 제한으로 CLI 인증, 네트워크 또는 터미널 접근이 막히면 해당 실행에 필요한 승인 절차를 사용합니다. `terminalOpen: null`은 현재 세션에서 터미널 프로세스의 생존 여부를 확인할 권한이 없다는 뜻입니다.

## 실행과 결과 확인

`<runner>`는 이 스킬 폴더의 `scripts/worker.mjs` 절대 경로입니다. 아래 인자는 각각 절대 경로를 사용합니다.

```text
node <runner> prepare [original-worktree]
node <runner> start <worktree> <prompt-file>
node <runner> follow-up <job-directory> <prompt-file> [--new-terminal]
node <runner> finish <job-directory> [published-directory]
node <runner> finish <job-directory> --applied [published-directory]
node <runner> finish <job-directory> --discard
node <runner> status <job-directory>
node <runner> cancel <job-directory>
```

1. `prepare`를 사용했다면 반환된 `cwd`를 `start`에 전달합니다. Windows PowerShell과 macOS Terminal.app에서 Antigravity 대화형 화면이 열립니다. 반환된 `jobDirectory`로 `status`를 주기적으로 확인하며 정상 완료까지 기다립니다. `starting`은 터미널 시작, `agy-starting`은 첫 훅 대기, `agy-running`은 작업 실행, `agy-settling`은 종료 이벤트 확인 단계입니다.
2. `review-ready`가 되면 화면 또는 `transcriptPath`에서 응답을 읽고 아래 검토 체크리스트를 적용합니다. 수정이 필요하면 `follow-up`으로 전달합니다. 이전 대화형 프로세스가 종료된 뒤 같은 터미널에서 다음 대화가 열립니다. 종료 요청과 새 훅 이벤트가 겹쳐 검토 상태가 해제되면, 상태를 다시 확인하고 새 `review-ready`에서 후속 요청을 재시도합니다. 별도 창을 원하면 `--new-terminal`을 사용합니다. 이전 터미널을 사용할 수 없고 작업 잠금이 정리된 상태라면 새 터미널을 엽니다. 각 자동 요청은 새로운 `agy` 대화이므로 후속 프롬프트에 필요한 문맥을 넣습니다.
3. 화면에 직접 새 프롬프트를 보내면 `changed-after-handoff`로 표시됩니다. 그 작업의 변경분을 다시 확인하고, 화면을 종료한 다음 자동 후속 요청을 보냅니다. `Ctrl+D`는 Antigravity 화면을 종료하고, `cancel`은 워커에 중단을 요청합니다. 빈 워커 터미널은 `Ctrl+C`로 닫습니다.
4. 후속 작업까지 마치면 Codex가 마지막 작업의 `jobDirectory`로 `finish`를 실행합니다. 실행기는 `prepare`가 만든 경로와 작업 종료 및 잠금 해제를 확인한 뒤 정리합니다.
   - **결과 반영 확인** — Codex가 변경분을 검토하고 필요한 결과가 원본이나 전달 위치에 반영됐음을 확인하면 `--applied`로 정리합니다. 원본에서 후속 편집을 했거나 파일 복사·스쿼시·체리픽으로 반영한 경우에도 사용할 수 있습니다. 임시 폴더는 워커 저장소 밖의 `published-directory`를 전달하고, Git 워크트리는 기록된 원본을 사용합니다. 기본 `finish`는 파일과 실행 권한이 일치하는 임시 폴더 및 원본 이력에 반영된 깨끗한 Git 워크트리를 검증해 제거합니다.
   - **중단·실패 후 정리** — `cancel` 뒤 종료 결과가 기록되고 화면과 잠금이 해제될 때까지 확인합니다. 필요한 변경이 있으면 먼저 반영하고 `--applied`로 정리합니다. 남길 변경이 없거나 폐기가 승인된 사본은 `--discard`로 제거합니다. `--discard`는 전달 위치를 받지 않습니다.
   - 종료가 확인되지 않거나 정리가 막히면 남은 경로와 이유를 보고합니다. 작업 폴더가 `cleanup-needed`이면 아래 복구 절차를 따릅니다.

### 검토 체크리스트

Codex는 매 검토에서 아래 항목을 확인하고, 변경의 성격과 영향에 맞춰 검증 범위를 정합니다.

1. **요청 충족** — 위임 프롬프트의 완료 조건을 실제 동작과 산출물에 대조합니다. 정상 사용 경로에서 조건이 충족되는지 확인합니다.
2. **변경 범위와 파일 배치** — 시작 전 상태와 현재 변경분(diff)·새 파일을 비교합니다. 기존 사용자 변경이 보존됐는지, 합의 범위 밖 변경이나 임시 파일·디버그 코드가 남았는지 확인합니다. 파일을 추가하거나 옮겼다면 프로젝트 지침과 유사 기능의 배치를 대조해 소스·테스트·설정·문서가 각 디렉터리의 역할에 맞는지 확인합니다. 새 디렉터리를 만들었다면 기존 구조 안에 배치할 수 있는지도 확인합니다.
3. **기존 동작과 실패 처리** — 영향을 받는 기존 호출부의 동작을 확인합니다. 입력·권한·데이터를 바꿨다면 중요한 실패에서 사용자가 보는 결과와 데이터의 최종 상태도 확인합니다.
4. **구현의 적절성** — 같은 책임을 맡는 기존 코드의 재사용 여부와 불필요한 추상화·의존성·설정, 오류를 숨기는 우회를 확인합니다. 인증이나 민감정보를 다루는 변경은 권한 검사와 로그·응답의 노출 여부도 점검합니다.
5. **최적화** — 변경된 실행 경로에서 반복 계산·조회·렌더링, 과도한 데이터 읽기·전송을 확인합니다. 새 의존성이나 초기화가 있다면 시작 시간·메모리·번들 크기 중 영향을 받는 지표를 살핍니다. 성능 개선이 완료 조건이거나 성능 저하가 의심되면 Codex가 같은 조건에서 변경 전후를 직접 비교합니다. 실제로 줄일 수 있는 비용이 확인되면 발생 조건, 영향, 개선 방법을 후속 요청에 적습니다.
6. **직접 검증** — Codex가 현재 변경분으로 필요한 검증을 직접 실행합니다. 버그 수정은 원래 실패 경로, 기능 변경은 실제 사용 경로를 우선 확인합니다.

실제 문제가 있으면 발생 조건, 관찰 결과, 기대 결과를 `follow-up`에 적고, 수정분과 영향을 받는 경로를 다시 검토합니다. 필수 검증에 실패했거나 실행하지 못했다면 이유와 남은 확인 범위를 보고합니다. 합의한 완료 조건과 필수 검증이 충족되면 작업 완료를 보고합니다.

## 작업 기록 보관

작업 기록은 `~/.codex/antigravity-worker/jobs/`에 저장합니다. `CODEX_HOME`을 지정했다면 그 위치를 기준으로 합니다. 후속 요청은 같은 저장 경로에 있는 터미널을 재사용할 수 있습니다.

다음 `start` 또는 `follow-up` 실행 시, 이 경로에서 터미널이 닫힌 지 24시간이 지났고 같은 터미널의 모든 작업에 최종 결과가 있으며 작업 폴더 잠금이 해제된 경우에만 작업 기록을 지웁니다. `finish`를 재시도할 수 있도록 전용 작업 폴더가 남아 있는 기록도 보관합니다. 현재 `follow-up`에서 참조하는 기록, `cleanup-needed`, 종료를 확인할 수 없는 기록 역시 보관합니다.

## 실패와 복구

- 터미널이 요청을 받는 기한은 45초입니다. `agy`가 시작되면 실행기는 프로세스 생존 여부, 현재 대화의 훅, 대화 로그 파일의 변경을 5초마다 `status.health`에 반영합니다. 첫 훅 대기가 45초를 넘거나 훅·로그 변경이 2분간 없으면 `quiet`로 표시하며 프로세스와 작업 잠금을 유지합니다. `checkedAt`은 점검 시각입니다. 실제 진행 여부는 `lastHookAt`과 `lastTranscriptChangeAt`으로 확인합니다.
- `quiet`가 이어지거나 점검 시각이 갱신되지 않으면 `workerPid`, `eventPath`, `transcriptPath`와 대화형 화면을 확인해 입력 대기·오류·계속 실행 중인 작업을 구분합니다. 새 활동이 관찰되면 정상 완료까지 기다립니다. 화면에서 필요한 입력을 확인하거나 종료가 필요한 근거가 생겼을 때 `cancel`로 중단할 수 있습니다. 이전 실행 기록의 `timed-out`은 당시 `phase`와 `eventPath`를 확인합니다.
- 현재 요청의 정상 `Stop` 이벤트와 `fullyIdle: true`가 확인되면 검토를 시작합니다. 파일 변경 알림이 누락될 때를 대비해 실행 중에는 이벤트 기록도 주기적으로 확인합니다. 완료 신호 없이 화면이 닫히거나 CLI가 예기치 않게 종료되면, 하위 작업이 남을 수 있어 `cleanup-needed`로 잠금을 유지합니다. 이때 `exitStatus`는 각각 `completion-missing` 또는 `failed`입니다. 워커는 작업 폴더의 `.agents/hooks.json`에 훅을 임시로 추가하며, 정상 완료 후 화면을 닫거나 중단이 확인되면 기존 설정을 복원하고 잠금을 해제합니다.
- macOS에서는 화면을 시작하기 전 터미널 입력 설정을 저장하고 화면이 닫힌 뒤 복구합니다. 복구에 실패하면 `terminalError`를 기록하고 해당 터미널은 후속 요청에서 교체합니다.
- `cleanup-needed`이면 다음 순서로 복구합니다.
  1. `workerPid`와 `terminalPid`로 이전 작업을 식별하고 Antigravity 및 그 작업이 시작한 프로세스가 종료됐는지 확인합니다.
  2. `hookPath`의 현재 설정을 `jobDirectory/original-hooks.json`과 대조해 임시 워커 항목만 정리합니다. 원래 설정이 없었다면 백업 파일도 없으며, 임시 훅만 들어 있는 파일은 제거할 수 있습니다. 다른 설정 변경은 보존합니다.
  3. `lockPath` 내용이 복구 중인 `jobDirectory`와 정확히 일치하는지 확인한 뒤 해당 잠금 파일을 제거합니다. 이미 생긴 작업 변경분을 검토하고 재실행합니다.
