# 실제 작업으로 전후 비교하기

실행 전후 비교를 요청받았거나 개선 효과를 실제로 측정할 때 이 문서를 읽습니다. 지침을 읽고 예상한 행동과 실제 실행에서 관찰한 행동을 구분하세요. 몇 가지 사례에서 통과했더라도 모든 작업에서 올바르게 동작한다고 보장할 수는 없습니다.

## 비교할 질문부터 정하기

어떤 변경으로 어떤 불필요한 작업을 줄이려는지, 어떤 행동은 유지해야 하는지 먼저 정합니다. 예를 들어 전체 테스트를 요구하는 조건을 바꿨다면, 단순 문구 수정에서 불필요한 테스트가 줄었는지와 중요한 상태 변경에서는 필요한 검증을 계속 수행하는지 함께 확인합니다.

비교 대상의 범위에 맞춰 조건을 정합니다.

- **전역 지침 비교:** 제공된 자료나 이미 확인한 사례 중 서로 다른 프로젝트·작업을 활용합니다. 한 저장소의 명령이나 정책을 다른 프로젝트에도 강제하지 않는지 확인합니다. 한 프로젝트에서만 비교했다면 다른 프로젝트에서도 효과가 있다고 일반화하지 않습니다.
- **프로젝트 지침 비교:** 전역·상위 지침은 같게 유지하고 해당 프로젝트의 지침만 바꿉니다. 저장소에 맞는 실행·검증 방법과 중요한 업무 제약이 유지되는지 확인합니다.
- **두 지침을 모두 바꾼 경우:** 원래 전역·프로젝트 지침의 조합과 수정한 두 지침의 조합을 비교합니다. 하위 지침이 없는 경로, 별도의 하위 지침이 있는 경로, 우선 적용 파일 때문에 다른 지침 파일이 선택되지 않는 경우 중 이번 변경과 관련된 사례를 고릅니다. 어느 쪽 변경이 결과에 영향을 줬는지 구분해야 할 때만 한쪽씩 바꿔 추가 비교합니다.

사용자가 반복하는 작업, 다시 지시해야 했던 상황, 이전에 실패한 사례를 우선합니다. 자료가 없으면 변경한 규칙을 확인할 수 있는 작은 예제를 만들고, 실제 사례가 아닌 테스트용 예제라고 밝힙니다. 아래에서 이번 규칙 변경과 관련된 사례만 고릅니다.

| 상황 | 관찰할 행동 |
| --- | --- |
| 분석만 요청 | 파일을 수정하지 않고 근거와 답변을 제공하는가 |
| 확정된 작은 수정 | 불필요한 질문·전체 검색 없이 필요한 변경과 검증을 마치는가 |
| 업무 규칙이 미정인 구현 | 결정을 추측하지 않고 필요한 부분만 질문하며 독립된 작업을 진행하는가 |
| 중요한 처리 실패 | 성공으로 숨기지 않고 사용자 결과·최종 상태를 확인하는가 |
| 기존 로컬 변경이 있는 수정 | 사용자 변경을 보존하는가 |
| 전역 지침과 다른 검증 명령을 쓰는 프로젝트 | 프로젝트의 명령을 따르면서, 이 명령과 충돌하지 않는 전역의 작업 보존 원칙도 지키는가 |
| 전역 지침이 없는 환경에서도 사용하는 프로젝트 지침 | 공통 규칙을 중복이라는 이유로 삭제해 필요한 지침을 잃지 않는가 |

“규칙을 요약해 봐”라는 요청은 어떤 지침을 인식했는지 확인하는 데 쓸 수 있습니다. 실제 작업에서 그 지침을 따르는지 확인한 결과로 대신하지 마세요.

## 같은 조건에서 실행하기

- 원본 지침과 수정한 지침을 각각 별도의 임시 작업 공간과 새 세션에서 실행합니다. 코드·데이터·요청·모델·추론 설정·권한·도구·훅은 같게 하고, 비교할 지침만 바꿉니다. 앞선 실행의 정답·결과·평가 의견을 다음 실행에 넘기지 않습니다.
- 실제로 어떤 지침 파일을 읽었는지 확인합니다. 비교 대상 이외의 전역·상위 지침과 우선 적용 파일도 같은 조건으로 맞춥니다. 수정안의 이름이나 위치가 달라 읽히지 않거나, 같은 전역 원문이 한쪽에만 중복으로 포함됐다면 비교 조건이 다릅니다. 비교를 위해 사용자가 실제로 쓰는 전역 지침을 교체하지 않습니다.
- 기존 로그인 정보나 키를 임시 작업 공간으로 복사하지 않습니다. 인증이 필요하면 도구가 지원하는 안전한 방법을 사용합니다. 작업 공간을 분리하면서 사용할 수 있는 도구가 달라졌다면, 그 조건에서 확인한 결과라는 한계를 밝힙니다.
- 사용자가 지정한 실행 환경을 따릅니다. CLI에서만 확인한 것을 데스크톱 앱에서도 확인했다고 보고하지 않습니다. 서브에이전트나 외부 API는 해당 대화에서 허용된 범위 안에서 사용합니다. 필요한 도구나 권한이 없으면 실행하지 못했다고 밝힙니다.
- 실제 프로젝트나 외부 서비스의 데이터를 바꾸지 않도록 테스트용 코드·데이터나 외부 서비스의 모의 구현을 사용합니다. 외부 서비스에 실제로 기록할 필요가 있다면 사용자가 승인한 범위에 포함되는지 확인합니다.

## 관찰과 판단

1. 실행 전에 어떤 결과가 나와야 통과인지 정합니다. 산출물, 파일 변경사항, 데이터 상태, 테스트 결과, 모델이 한 질문과 실행한 도구를 근거로 판단합니다. “더 좋아 보인다”거나 지침 문구를 그대로 되풀이했다는 이유만으로 통과시키지 않습니다.
2. 작업의 성공·실패·중단·재시도와 필요한 검증을 수행했는지부터 비교합니다. 의도적으로 바꾼 행동은 별도로 평가합니다. 원본과 다르다는 이유만으로 실패로 판단하지 않습니다.
3. 측정할 수 있는 항목만 기록합니다. 소요 시간, 도구 호출 수, 사용자가 다시 지시한 횟수, 입력·출력·캐시·추론 사용량을 구분합니다. 확인할 수 없는 값을 0으로 채우거나 추정값을 실제 측정값처럼 제시하지 않습니다.
4. 파일의 바이트 수가 줄었다는 사실만으로 토큰 수나 비용의 감소를 계산하지 않습니다. 비용을 계산한다면 실제 사용한 모델과 사용량 종류를 확인하고, 확인 시점의 공식 가격을 적용합니다. 계산한 비용과 실제 청구된 비용을 구분합니다.
5. 중요한 규칙을 빠뜨리거나 필요한 산출물을 만들지 못했다면 수정안을 고치거나 원본을 유지합니다. 원본에서도 같은 문제가 발생했다면 양쪽에서 확인된 한계로 기록합니다.
6. 소수의 사례나 한 번의 실행 결과는 예비 결과라고 밝힙니다. 차이가 불분명하거나 실패가 발생했을 때만 승인된 시간·사용량 범위 안에서 다시 실행합니다. 필요하면 실행 순서도 바꾸되, 원하는 결과가 나올 때까지 반복하지 않습니다.

어떤 사례를 어떤 조건에서 실행했는지, 통과 여부와 사용량은 어땠는지 함께 설명합니다. 결과가 달라진 원인을 확인하지 못했다면 특정 변경 때문이라고 단정하지 마세요. 실행 근거가 부족하면 “파일 크기와 규칙 누락 여부는 확인했지만, 실제 행동·시간·비용이 개선됐는지는 확인하지 못했다”처럼 구분해 보고합니다.
