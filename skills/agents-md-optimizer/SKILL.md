# AGENTS.md 최적화

모델이 지침을 이해하는 데 드는 부담과 불필요한 작업을 줄이되, 사용자가 요구한 행동은 유지하는 것이 목표입니다. 지침이 짧아졌다는 이유만으로 개선됐다고 판단하지 않습니다. 사용자가 요청한 파일과 작업 범위 안에서 진행하세요.

**지침의 적용 범위 확인 → 범위에 맞는 평가 → 요청한 파일 수정 → 변경 결과 확인** 순서로 진행합니다. 전역 지침과 프로젝트 지침을 각각 수정할 수 있으며, 둘 다 요청한 경우에만 둘 다 수정합니다.

프로젝트 지침의 초기 작성이나 프로젝트 용어·실행·검증 정보 보강을 요청받으면 [프로젝트 지침 작성 기준](references/project-bootstrap.md)을 읽습니다. 요청 범위 구분(1절)과 파일 반영·복구 원칙(5절)은 초기 작성·보강에도 공통으로 적용합니다. 기존 지침의 평가·최적화는 아래 절차를 따릅니다. 일반 코드 작업 중에 요청하지 않은 지침 파일을 만들지 않습니다.

## 1. 수정할 파일과 지침의 적용 범위 확인

- 분석, 수정안 작성, 직접 수정, 실행 전후 비교 중 무엇을 요청했는지 확인합니다. 수정 요청이면 파일에 반영하고, 분석이나 수정안만 요청했다면 원본을 바꾸지 않습니다. 이미 명확한 내용은 다시 묻지 않습니다.
- 파일의 현재 내용과 기존 변경사항을 확인합니다. 그 파일이 전역 지침인지 프로젝트 지침인지는 위치나 제목만으로 단정하지 말고, 실제로 어디에 적용하는지 확인합니다. 저장소 루트의 파일도 여러 프로젝트에 배포할 전역 지침의 원본일 수 있습니다.
- 사용하는 도구에 따라 지침 파일명과 읽는 방식이 다를 수 있습니다. `AGENTS.md` 이외의 파일은 사용자가 지정했거나 해당 도구가 실제로 읽는 지침 파일임을 확인했을 때 다룹니다. 이 스킬이 전역에 설치됐다고 해서 수정 대상도 전역 지침인 것은 아닙니다.
- 요청한 작업에 적용되는 상위·하위 지침과 관련 훅·스킬만 확인합니다. 모든 저장소나 설치된 스킬을 검색하지 않습니다.
- 프로젝트 지침을 생성·수정할 때는 기존 문서·설정·템플릿과 같은 책임의 대표 구현에서 확인한 공통 규칙·반복되는 틀을 유지합니다. 적용 범위·예외·대표 경로를 지침에 남기고, 축약·일반화·중복 제거를 이유로 임의로 누락하거나 다른 틀로 바꾸지 않습니다. 관찰된 관례와 확정된 업무 규칙은 구분하며, 변경이 필요하면 근거와 달라지는 행동을 설명하고 해당 변경에 대한 사용자 요청·확인 범위 안에서 진행합니다.
- 같은 디렉터리에서 어떤 지침 파일을 먼저 선택하는지, 상위·하위 지침이 충돌하면 무엇을 따르는지, 크기 제한이 있는지 등은 사용하는 도구에 따라 확인합니다. 도구의 동작을 확인해야 할 때는 해당 도구의 최신 공식 문서를 참고하되, 문장을 다듬는 데 필요하지 않은 조사까지 하지는 않습니다.

### 범위별 최적화 기준

| 대상 | 필요한 내용 | 평가할 내용 |
| --- | --- | --- |
| 전역 지침 | 여러 프로젝트에 공통으로 적용할 협업 방식, 권한과 기존 작업 보존 원칙, 사용자가 선호하는 언어와 도구 | 특정 저장소의 경로·명령·업무 규칙을 다른 프로젝트에도 강제하는가? 간단한 작업에 과도한 절차를 요구하는가? |
| 프로젝트 지침 | 해당 저장소의 실행·검증 명령, 코드 구조, 수정해도 되는 범위, 중요한 업무 규칙과 데이터 제약 | 실제 코드·설정·확인된 업무 규칙과 일치하는가? 전역 지침을 불필요하게 반복하는가? 일부 하위 디렉터리에만 적용할 내용을 전체에 강제하는가? |

- **전역 지침을 수정할 때:** 특정 저장소에 종속되지 않고 여러 프로젝트에서 쓸 수 있는지 평가합니다. 특정 프로젝트의 사례가 필요하면 이미 확인한 내용이나 제공된 자료를 활용합니다. 모든 프로젝트를 조사하지 않습니다. 프로젝트 지침으로 옮길 내용을 제안할 수는 있지만, 요청하지 않은 프로젝트 파일까지 수정하지 않습니다.
- **프로젝트 지침을 수정할 때:** 해당 저장소의 코드와 설정을 확인해 명령·구조·제약이 맞는지 평가합니다. 실제 적용되는 전역·상위 지침은 필요한 범위에서 참고만 하고 변경하지 않습니다. 확인되지 않은 업무 규칙을 새로 만들지 않습니다. 전역 지침을 확인할 수 없으면 전역과의 중복·충돌은 판단하지 못했다고 밝힙니다.
- **두 지침을 모두 요청했을 때:** 각각의 기준으로 평가한 뒤 요청한 작업을 수행하고, 두 지침을 함께 읽었을 때 실제로 어떤 규칙이 적용되는지 확인합니다. 같은 디렉터리에서 읽을 파일을 선택하는 규칙과, 상위·하위 지침 사이에서 우선할 규칙을 정하는 방식을 구분합니다. 한 도구에서 확인한 적용 방식을 다른 도구에도 그대로 적용하지 않습니다.
- 프로젝트 규칙을 전역 지침으로 옮기면 다른 프로젝트에도 영향을 줄 수 있습니다. 전역 규칙을 프로젝트 지침으로 옮기면 적용 범위가 줄어듭니다. 이 차이를 설명하고, 요청 범위를 벗어나는 이동은 반영하지 않습니다.
- 프로젝트 지침을 전역 지침 없이도 배포·사용해야 하거나 공통 원칙을 반복해서 명시할 이유가 있다면 해당 내용을 유지할 수 있습니다. 같은 문장이 있다는 이유만으로 삭제하거나, 사용자의 전역 지침이 모든 실행 환경에 존재한다고 가정하지 않습니다.

## 2. 개선할 지시 찾기

다음 기준으로 중복되거나 혼동을 주거나 불필요한 작업을 요구하는 지시를 찾습니다.

- **중복:** 같은 행동을 여러 곳에서 반복하는가? 문장이 비슷해도 적용 조건이나 예외가 다르면 그 차이를 유지합니다.
- **충돌과 모호함:** 같은 상황에서 서로 다른 행동을 요구하는가? 어떤 지시를 따라야 하는지 분명한가?
- **과도한 의무:** 간단한 작업에도 전체 검색·테스트·보고·재검토를 반복하게 하는가? 어떤 경우에 필요하고 언제 끝낼지 더 명확히 할 수 있는가?
- **지침을 둘 위치:** 모든 작업에 필요한 원칙인가, 특정 프로젝트나 작업에만 필요한 절차인가? 옮긴 위치에서도 필요한 때에 읽히는지 확인합니다. 규칙을 추가할 때는 기존 테스트·린트·타입 검사로 확인할 수 있는지와 유지 비용을 먼저 검토하고, 프로젝트에 한정된 규칙은 전역 지침으로 일반화하지 않습니다.
- **잘못된 정보:** 존재하지 않는 파일·명령·기능이나 도구가 지원하지 않는 동작을 전제로 하는가?
- **삭제의 영향:** 이 문장을 없애면 어떤 유용한 행동을 놓칠 수 있는가? 삭제해도 된다는 근거가 부족하면 유지합니다.

“모델이 알아서 할 것”이나 “상위 지침에도 있다”는 이유만으로 사용자가 명시한 선호를 삭제하지 않습니다. 사용자가 정한 규칙과 도구의 기본 동작을 구분하세요. 줄일 비율을 먼저 정하거나, 문장을 무조건 짧게 만들거나 영어로 바꾸지 않습니다.

## 3. 수정안 작성과 의미 변화 설명

- 표현만 줄이는 수정과 실제 행동을 바꾸는 수정을 구분합니다. 표현만 줄일 때는 적용 조건·예외와 금지·허용·의무의 강도를 유지합니다.
- 규칙을 삭제하거나 의무를 권고로 바꾸는 등 의미가 달라지면 **원래 요구한 행동 → 바뀐 행동 → 기대하는 효과 → 약해지는 보호 조치나 확인하지 못한 점**을 설명합니다. 표현만 달라진 문장을 모두 표로 나열할 필요는 없습니다.
- 요청 범위에 포함된 삭제·완화는 진행할 수 있습니다. 업무 결과나 사용자 선호를 어느 쪽으로 바꿀지 결정되지 않은 항목만 질문하고, 그 답변이 필요하지 않은 정리는 계속합니다.
- 효율을 높인다는 이유로 권한 제한, 비밀값 보호, 사용자 작업 보존 원칙을 우회하지 않습니다. 필요한 검증을 없애서 줄인 시간을 성능 개선으로 보고하지 않습니다.
- 절차를 훅이나 스킬로 옮겼다는 이유만으로 반드시 실행되거나 항상 읽힌다고 주장하지 않습니다. 요청하지 않은 훅·설정·설치 경로까지 바꾸지 않습니다.
- 여러 파일을 검토했다면 수정안마다 대상 파일을 표시합니다. 프로젝트의 예외 규칙이 의도된 것인지 불분명하면 전역 규칙에 맞춰 임의로 바꾸지 않습니다.
- 비교용 수정안은 에이전트가 현재 지침으로 읽는 파일과 별도로 저장합니다. 수정안을 작성한 것과 실제 적용할 파일에 반영한 것을 구분합니다.

## 4. 파일 크기와 실제 행동을 나누어 확인

원본과 수정안의 파일 크기는 다음 도구로 비교할 수 있습니다. 이 도구는 파일을 바꾸지 않고 UTF-8 바이트 수, 문자 수, 줄 수와 파일 내용의 해시를 출력합니다. 아래 경로를 실제 경로로 바꿔 실행하세요. `<스킬 경로>`는 이 `SKILL.md`가 있는 디렉터리입니다.

```sh
python3 "<스킬 경로>/scripts/compare_size.py" "<원본 경로>" "<수정안 경로>"
```

`change_percent`는 `(수정안의 값 - 원본의 값) / 원본의 값 × 100`입니다. 음수면 줄었다는 뜻이며, 원본의 값이 0이면 비율을 계산할 수 없어 `null`을 출력합니다. 이 도구는 토큰 수, 모델 성능, 실행 비용을 측정하지 않습니다. 토큰 수가 필요하면 해당 모델에 맞는 토큰 계산 도구를 사용하고 계산 기준을 밝히세요.

직접 수정한 뒤에는 바꾼 부분을 원문과 대조합니다.

- **언제 적용하는가:** 적용 대상·조건·예외가 수정안에도 남아 있는지 확인합니다. 조건을 생략해 적용 범위를 넓히거나 좁히지 않았는지 봅니다.
- **무엇을 해야 하는가:** 원문이 요구한 행동과 의무의 강도가 어디에 남아 있는지 확인합니다. 문장을 합치거나 옮겼다면 그 위치에서 확인합니다.
- **사라진 요구가 있는가:** 의도한 삭제인지 실수로 빠진 것인지 구분합니다. 누락은 복원하고, 의도한 삭제라면 이유와 달라지는 행동을 설명합니다.

이 대조는 바꾼 부분에 한정하며, 모든 문장을 표로 보고할 필요는 없습니다. 실행 효율 비교를 요청받았거나 개선 효과를 입증해야 한다면 [실행 비교 방법](references/evaluation.md)에 따라 실제 작업으로 비교합니다. 실행 환경이 없거나 비교하지 않았다면 문서 내용으로 확인한 사항만 보고하고, 시간이나 비용이 줄었다고 단정하지 않습니다.

## 5. 파일에 반영하고 결과 보고

- 수정 전의 전체 내용을 복구할 수 있게 준비합니다. 아직 커밋하지 않은 변경이 있다면 Git만으로 복구할 수 있다고 가정하지 않습니다. 복구본도 원본처럼 접근 권한을 보호하고 민감한 내용을 출력하지 않습니다.
- 반영 직전에 파일이 분석할 때 읽은 내용과 같은지 확인합니다. 달라졌다면 새 변경사항을 대조해 다른 작업을 덮어쓰지 않습니다.
- 요청한 범위의 변경을 반영하고 필요한 검증을 수행합니다. 전역 설치, 다른 도구로의 복사·동기화, 커밋·푸시는 각각 요청받은 범위에서만 진행합니다.
- 결과는 **수정한 파일과 적용 범위 → 바뀐 행동과 의미 → 예상 효과 또는 실제 측정 결과 → 검증한 내용과 남은 한계** 순서로 설명합니다. 전역과 프로젝트를 함께 검토했다면 각 파일의 결과와 함께 적용했을 때의 결과를 구분합니다. 문서 내용 검토, 크기 비교, 실제 작업 실행 중 무엇을 했는지 명확히 밝힙니다. 나아질 부분이 없다면 원본을 유지할 수 있습니다.
