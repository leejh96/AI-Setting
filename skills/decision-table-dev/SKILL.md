# 결정 테이블 기반 구현·테스트 (Decision Table Dev)

목표는 복잡한 분기 로직을 다루기 전에 **조건 × 결과 결정 테이블(Decision Table)**로 먼저 구조화해 잘못된 추측으로 인한 재작업을 줄이고, 확정된 표를 **Guard Clause 구현**과 **테이블 주도 테스트(Table-Driven Test)**에 연결하는 것입니다. 한 행을 여러 테스트로 검증할 수 있습니다.

**적용 판단 ➔ 결정 테이블 작성·미확정 분리 ➔ Guard Clause 중심 구현 ➔ 테이블 주도 테스트 매핑 ➔ 검증 보고** 순서로 진행합니다.

---

## 1. 적용 대상과 작업 범위 확인

- **적용 대상:** 입력 검증, 권한 체크, 도메인 상태 전이, 멱등 처리, 외부 호출 성공·실패 등 **결과가 갈리는 분기가 2개 이상인 백엔드 기능 구현·수정·리팩터링 및 분기 설계·리뷰**에 적용합니다.
- **제외 대상:** 분기가 없는 단순 조회와 업무 분기·반환 결과·상태 변경에 영향을 주지 않는 단순 설정·문구 변경에는 표 작성을 생략합니다. 수정 줄 수는 적용 제외 기준으로 삼지 않습니다.
- **요청 유형별 진행 범위:**
  - **설계·분석·리뷰 요청:** 코드를 수정하지 않고 결정 테이블과 누락·충돌 분기 또는 `확인 필요` 사항만 제시합니다.
  - **구현·수정·리팩터링 요청:**
    - 모든 행이 `확정`이면 별도 승인 대기 없이 결정 테이블을 기준으로 구현·테스트·검증까지 바로 진행합니다.
    - `확인 필요` 행이 있으면 표와 질문을 먼저 제시하고, 미확정 결정에 영향을 받는 코드 경로는 추측해 구현하지 않고 보류합니다(미확정 결정과 무관하게 독립적으로 완결 가능한 작업만 선행).

---

## 2. 구현 전 결정 테이블(Decision Table) 압축

코드를 길게 작성하기 전에 관련 기존 코드·타입·계약을 필요한 최소 범위만 확인한 뒤, 분기 조합을 아래 형태의 짧은 표로 먼저 정리합니다.

아래는 정상 해지·중복 요청·권한 차단 정책이 이미 확인되었고, 외부 타임아웃 정책만 미확정인 예시입니다. 상태 코드와 처리 정책을 다른 작업의 기본값으로 사용하지 않습니다.

```markdown
| 케이스 | 조건 (권한·상태·입력·외부 응답) | 기대 결과 (반환값·상태 코드·예외) | 상태 변경·부수효과 | 구분 |
| :--- | :--- | :--- | :--- | :---: |
| #1 | 본인 + ACTIVE + 외부 200 | 200 OK (해지 완료) | 상태 CANCELED 저장, 이벤트 발행 | 확정 |
| #2 | 본인 + 이미 CANCELED | 409 Conflict (중복 해지) | 변경 없음 (외부 호출 생략) | 확정 |
| #3 | 권한 없음 (타인, 상태 `-`) | 403 Forbidden | 변경 없음 (외부 호출 생략) | 확정 |
| #4 | 본인 + ACTIVE + 외부 타임아웃 | ❓ 즉시 502 반환 vs 재시도 큐 적재 | 확인 후 결정 | 확인 필요 |
```

### 표 작성 규칙

- **핵심 축만 압축:** 코드의 모든 세부 변수를 나열하지 말고, 비즈니스 결과나 데이터 상태를 바꾸는 조건 축(권한, 현재 상태, 입력 유효성, 외부 응답 등)만 열에 포함합니다.
- **무관한 조건 묶기:** 앞선 조건만으로 결과가 확정되어 나머지 조건이 결과에 영향을 주지 않으면 `-`(무관)로 묶어 행 수를 최소로 유지합니다(보통 3~10행).
- **확정과 미확정 분리:**
  - 기존 코드·문서로 확인한 현재 동작과 이번 요청에서 확정된 규칙을 구분하고, 각 행의 근거를 표나 인접 설명에 짧게 남깁니다. 요청에서 유지하기로 한 기존 계약은 재확인 없이 활용할 수 있지만, 새로 정하거나 변경할 업무 규칙을 기존 구현만으로 `확정`하지 않습니다.
  - 기획·업무 규칙이 누락되었거나 기존 계약과 충돌하는 행(예: 외부 실패 시 롤백 vs 부분 성공 허용)은 추측해 채우지 않고 `확인 필요`로 표시합니다.

## 3. 결정 테이블 ➔ Guard Clause 구현 변환

확정된 결정 테이블의 각 행을 코드의 실행 순서와 대조해 구현합니다.

1. **차단·예외·멱등 행 먼저 배치 (Guard Clauses):**
   - 권한 부족(`#3`), 입력 오류, 이미 처리된 상태(`#2`)처럼 **상태 변경이나 외부 비용 발생 전에 걸러야 하는 행**을 함수 상단의 조기 반환(Early Return) 또는 예외 던지기로 배치해 `if-else` 중첩을 줄입니다.
   - **평가 우선순위 점검:** 기존 인증 계층과 이번 요청에 적용되는 응답 계약을 확인해 검사 순서를 정합니다. 여러 차단 조건이 동시에 성립할 때의 응답·상태 노출이 달라진다면 그 조합을 표에 반영합니다. 필요한 우선순위가 불명확하면 `확인 필요`로 분리하고 질문하며, 입력 검증·인증·권한·상태 검사의 순서를 관례로 정하지 않습니다.
2. **외부 I/O와 상태 변경 순서 점검:**
   - 표의 `상태 변경·부수효과` 열을 기준으로, 외부 호출이나 쓰기 실패 시 최종 데이터 상태가 의도한 복구·롤백 규칙과 일치하는지 확인합니다.
3. **기존 구조 존중:**
   - 프로젝트의 기존 예외 클래스, 응답 포맷, 공통 검증 모듈을 재사용하며 요청 범위를 넘는 구조 개편은 하지 않습니다.

---

## 4. 결정 테이블 ➔ 테이블 주도 테스트(Table-Driven Test) 연결

변경의 위험도에 맞춰 단위·통합 테스트를 작성하거나 갱신할 때는, 케이스마다 비슷한 테스트 함수를 복사·붙여넣기하지 않고 **결정 테이블의 각 확정 행을 하나 이상의 테스트 데이터 항목에 연결**합니다.

- **행 번호와 시나리오 이름 연결:** 테스트 배열의 각 항목에 표의 케이스 식별자(`#1 정상 해지`, `#2 중복 해지 차단`, `#3 권한 없음` 등)를 포함해, 실패 시 어느 분기가 깨졌는지 즉시 알 수 있게 합니다.
- **압축한 행 확장:** `-`로 묶은 조건도 권한·경계값·검사 순서의 회귀를 놓칠 수 있으면 여러 테스트로 확장합니다. 예를 들어 `#3`은 `ACTIVE`와 `CANCELED` 모두에서 권한 차단을 확인합니다. 모든 조합을 기계적으로 나열할 필요는 없습니다.
- **결과와 부수효과 함께 검증:** 표의 `기대 결과`(반환값·상태 코드·예외)뿐 아니라 `상태 변경·부수효과`도 검증합니다. 저장 결과는 변경한 메모리 객체만으로 판단하지 않고 저장소에서 다시 조회해 최종 상태를 확인합니다. 외부 호출·이벤트는 실행 횟수와 필요한 인자를 확인하고, 차단 시에는 호출되지 않았는지도 검증합니다.
- **검증 방식이 다르면 테이블 분리:** 정상 반환 케이스와 예외 발생(throw) 케이스를 한 배열에 억지로 합쳐 테스트 본문 안에 `if-else` 분기를 만들지 않고, 검증 방식이 다르면 정상 케이스와 예외·차단 테이블로 나누어 작성합니다.
- **기존 테스트 스타일 우선:** 저장소에 이미 사용하는 매개변수화 테스트 방식이 있으면 그 관례를 따릅니다. 언어·프레임워크별 기본 작성 예시가 필요할 때만 [언어별 테이블 주도 테스트 패턴](references/test-patterns.md)을 참고합니다.
- **과잉 추가 금지:** 테스트 프레임워크가 없거나 사소한 변경이어서 테스트 작성이 불필요한 경우에는 새 의존성을 임의로 설치하지 않고, 실제 확인한 검증 방법과 남은 한계를 보고합니다.

---

## 5. 검증 및 완료 보고

- 구현한 코드의 분기, 결정 테이블의 확정 행, 실행한 테스트 케이스가 서로 빠짐없이 대응하는지 확인합니다. 압축한 행에서 추가로 검증한 권한·경계값·우선순위 조합도 확인합니다.
- 완료 보고에서는 이미 제시한 표 전체를 불필요하게 반복하지 않고, **결정 테이블의 핵심 분기(또는 변경된 판단) ➔ 실제 실행한 테스트·검증 결과 ➔ 미확인 범위나 남은 한계**를 간결하게 제시합니다. 테스트를 실행하지 못했거나 일부 분기만 확인한 경우 구현 반영과 동작 확인 여부를 구분해 밝힙니다.
