# 원인 추적 디버깅

**실패 조건 확인 → 원인을 구별할 증거 수집 → 최소 수정 또는 필요한 조치 → 같은 실패 경로 검증**으로 진행합니다. 고정된 가설 수나 긴 보고서를 요구하지 않습니다.

## 1. 실패와 작업 범위 확인

- 사용자가 원하는 것이 원인 설명인지 수정인지 구분하고, 기대 동작·실제 동작·실패 명령·환경·재현 조건을 필요한 범위에서 확인합니다. 이미 제공된 내용이나 로컬에서 확인할 수 있는 사실을 다시 묻지 않습니다.
- 관련 변경과 기존 로컬 작업을 구분합니다. 원인 분석만 요청하면 증거와 가설을 제시하고, 수정 요청이면 원인을 좁힌 뒤 허용된 수정·검증까지 진행합니다.
- 수정 요청에서 원인이 명백한 단순 오류는 직접 수정하고 관련 경로를 확인합니다. 모든 버그에 로그 추가, 재현 프로젝트, 가설 문서나 전체 테스트를 강제하지 않습니다.

## 2. 원인을 구별하는 확인

- 실패 명령과 관련 진입점·호출부·테스트부터 확인합니다. 필요한 경우 최소 재현을 시도하며, 실패 전후의 상태와 오류가 발생한 경계를 확인합니다. 변경 위치·중요한 영향·검증 방법이 판단되면 무관한 탐색을 멈춥니다.
- 코드 결함, 의존성·버전 차이, 환경·파일 권한, 외부 서비스 실패를 관찰한 증거로 구분합니다. 하나의 오류 문자열이나 종료 코드만으로 원인을 확정하지 않습니다.
- 현재 증거에 맞는 소수의 가설을 세우고, 각 가설을 지지하거나 배제할 수 있는 가장 작은 확인을 선택합니다. 코드 읽기만으로 충분하면 추가 실험을 강제하지 않습니다. 여러 추측성 수정을 한꺼번에 적용해 원인을 가리지 않습니다.
- 같은 명령의 재시도는 달라진 조건이나 일시적 실패를 의심할 근거가 있을 때 수행합니다. 재시도로 무엇을 확인할지 정하고, 같은 실패만 반복되면 새 증거를 얻을 방법이나 부족한 정보를 제시합니다.
- 권한 부족이면 허용된 승인 절차를 사용합니다. 권한·인증·검사를 끄거나 비밀값을 출력해 우회하지 않습니다. 의존성 설치·업그레이드, 외부 상태 변경이나 운영 데이터 접근은 원래 요청과 권한 범위 안에서만 수행합니다.
- 추가 로그가 필요하면 필요한 값만 최소로 수집합니다. 비밀값·개인정보를 기록하거나 비공개 코드를 외부 검색에 보내지 않습니다. 임시 진단 코드와 지속적으로 필요한 관측 코드를 구분하고, 임시로 추가한 코드는 검증 후 제거합니다.

## 3. 수정과 확인

- 확인한 원인에 맞는 위치만 최소 수정합니다. 오류를 삼키는 catch, 무조건적인 재시도, 검사 비활성화나 근거 없는 기본값으로 성공처럼 보이게 하지 않습니다. 기존 계약·실패 처리 정책을 유지하고, 새 업무 정책이 필요하면 해당 결정만 질문합니다.
- 원래 실패한 입력·명령·실행 경로로 해결 여부를 확인하고, 영향에 맞는 인접 정상·실패 분기를 확인합니다. 회귀 가능성이 있는 동작에는 필요한 테스트를 추가·수정하되 구현을 그대로 따라 쓰는 테스트나 새 프레임워크를 강제하지 않습니다.
- 환경 조치로 해결됐다면 불필요한 코드 변경은 하지 않습니다. 일부 실패만 해결됐으면 나머지를 별도로 추적합니다.
- 재현할 수 없거나 근거가 부족하면 원인을 확정했다고 말하지 않습니다. 수정이 필요하지만 판단을 막는 정보가 남았으면 그 정보와 다음 확인을 제시하고 관련 수정만 보류합니다. 불확실한 수정안을 이미 검증된 해결책처럼 반영하지 않습니다.

## 4. 결과 전달

원인 또는 가장 유력한 가설 → 이를 구별한 근거 → 실제 변경·환경 조치 → 원래 실패 경로와 영향 범위의 검증 → 남은 실패·미확인 사항 순서로 짧게 보고합니다. 문서·소스 확인과 실행 재현을 구분하고, 실행하지 못한 이유를 밝힙니다. 요청이나 프로젝트 규칙이 없으면 별도 진단 문서를 만들지 않습니다.
